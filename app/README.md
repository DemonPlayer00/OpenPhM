# OpenPhM 应用骨架（Linux 优先）

制谱器的第一版 UI 骨架。**开发与验证都在 Linux（Wayland/KDE）**；Windows 侧能**交叉编译出 exe**
并在 Wine 上跑通（GUI 窗口、无头渲染、中文显示都验过），见「Windows exe（交叉编译）」一节 ——
但**没有在真 Windows 机器上跑过**。中文**自带字体**（内嵌思源黑体，不依赖系统字体），见「字体」一节。

## 启动到底在等什么（`--trace-startup`）

启动慢在哪，猜不如量：`opm-app --trace-startup`（或 `OPM_TRACE_STARTUP=1`）会把
"进程启动 → 首帧画完"之间每一步的**累计**与**本步**耗时打出来。本机（AMD 610M 核显 + Vulkan，
debug 构建，热启动取 5 次中位）实测：

| 阶段 | 中位耗时 | 说明 |
|---|---|---|
| 参数解析 / 横幅 / 文档 / 最近打开列表 | ~1 ms | 我自己的代码，几乎不花时间 |
| **7z 探测** | **7–22 ms** | 起一次 `7z i` 真跑一遍（"能不能调用"才算数，见下） |
| —— 到此才交棒给 eframe —— | **~22 ms** | |
| winit 事件循环 + 开窗口 + wgpu 实例 + Vulkan loader/ICD | **~720 ms** | **最大块**，波动也最大（实测 430–800 ms） |
| 设备创建 + surface 配置 + eframe 装配（到 `App::new`） | **~630 ms** | 第二大块 |
| `App::new` + Playfield 回调资源 | ~0.2 ms | 快 |
| **中/韩文字体装载** | **~220 ms → 现 ~37 ms** | 改成**内嵌字体**后：不读盘、不起 `fc-match`/`fc-scan`（三个样本 32.8/36.0/36.9 ms，其中还含读 19 MB 系统 TTC 的韩文回退）。见「字体」一节 |
| **首帧 UI 构建** | **~300 ms** | 首帧字体图集/度量 + 画启动页 |
| **合计到"启动页画完"** | **~1.9 s**（最好一次约 1.0 s） | 之后还要一帧交给合成器显示 |

**最大的一块（也是"1 秒"里最出乎意料的）**：**别去唤醒独显**。

wgpu 枚举适配器时，Vulkan loader 会把 ICD 目录里的**所有**驱动都加载起来 —— 包括 `nvidia_icd.json`，
而"加载 NVIDIA 的 Vulkan ICD"会把**运行时断电（`runtime_status=suspended`）的独显唤醒**。
实测（读 `/sys/bus/pci/devices/0000:01:00.0/power/runtime_status`）：

| 条件 | 启动到首帧画完 | 跑完之后独显 |
|---|---|---|
| 加载全部 ICD（旧行为） | **4028 ms** | `active`（被唤醒） |
| 默认现在：**摘掉 NVIDIA 的 ICD** | **1392 ms** | `suspended`（**没被碰**） |

也就是说：光是"把一块断电的独显叫醒"就要 ~2.6 s，而且用户根本没打算用它。现在的规则是
**默认只加载非 NVIDIA 的 Vulkan ICD**（`VK_DRIVER_FILES` 指向那几个 json），并且只在
"Linux + 没显式指定 ICD + 没显式要独显 + 本机还有别的 ICD"时才这么做 ——
**单独显机器**（只有 NVIDIA）与**显式要独显**（`prime-run` / `OPM_GPU=discrete` / `DRI_PRIME`）一律不干预，
后者实测照旧选中 NVIDIA。启动日志里有一行 `图形 ICD : …（保留 N 个：…）`，摘了谁、为什么，一眼可见。
**这些一律只在 Linux 生效** —— 平台边界见下面的「平台契约」一节（Windows 上连 ICD 目录都不扫）。

**局限**（写清楚）：只能按**文件名**认厂商，分不出"同厂商的核显与独显"（AMD 平台的 `radeon_icd` 可能是独显，
那种机器仍会被枚举到）；另外 GL 后端那条路无法这样过滤（所以"没有 Vulkan"时仍可能碰到独显）。

**另一块已经拿掉的**：wgpu 默认把所有后端都初始化一遍 —— 在 Linux 上连 **GL（Mesa EGL/GLX）也一起拉起来**。
现在**探测到 Vulkan 可用就只开 Vulkan**（探测本身不触发初始化：只看 ICD json 与 `libvulkan.so.1` 在不在），
实测（交替 6 轮、逐对比较）：

| 阶段 | 全后端 | 仅 Vulkan | 差 |
|---|---|---|---|
| 适配器枚举完成 | 703 ms | 599 ms | **−143 ms** |
| 到 `App::new` | 1323 ms | 1153 ms | **−185 ms** |
| 到"启动页画完" | 2087 ms | 1909 ms | **−201 ms** |

**回退一点没丢**：探测不到 Vulkan（没有 ICD json / 没有 loader，或 `VK_DRIVER_FILES` 指了个不存在的文件）
就仍然开全后端 —— 这时 GL 那条路才是唯一能出图的（实测 `VK_DRIVER_FILES=/nonexistent.json`：退回全后端、
用 GL 的 AMD 适配器正常出图）。开关：`OPM_BACKEND=vulkan|all`（默认自动）；用户设了 `WGPU_BACKEND` 时一律不抢。

**结论**：自己的代码只占 ~22 ms；剩下的 ~1.2 s 是 winit/wgpu/驱动/合成器 + 字体与首帧
（拆开后的口径见上面的表：摘 ICD 之后"到首帧画完"中位 ~1.39 s，最好一次 274 ms）。
再往下压只剩这些**量过的**选项（都不改默认）：`WGPU_VALIDATION=0 WGPU_DEBUG=0`（debug 构建默认开着
wgpu 校验，实测设备创建 −92 ms；release 本来就没有）、7z 探测并行化（~20 ms）、
中/韩文字体延迟加载（~100–150 ms，代价是首现韩文那一帧慢一下）。

注意别把"第二帧"读成启动慢：空闲心跳是 1 fps，第二帧本来就晚 ~0.5 s 到（`--idle-fps` 控制），
那是**节奏**不是启动。

## 运行

```sh
cd app
cargo run --release -- --notes 20000          # 正常交互
cargo run --release -- --bench 300            # 跑 300 帧后打印统计并退出
cargo run --release -- --stress --notes 200000 --bench 300   # 20 万实例压力
cargo run --release -- --scale 1.5 --verify-align            # 分数缩放 + 对齐自检
```

参数：`--notes N` `--bench N` `--stress` `--scale F` `--idle-fps F` `--idle-seconds S` `--ws compose|timeline|perform|debug`
      `--fps-cap F` `--lookahead S` `--verify-align` `--width/--height`
      `--doc FILE`（载入真实 opm 谱面）`--control [auto|PATH]`（开控制通道）`--verbose-updates`（每次广播/重建打一行）
      `--shot PATH --shot-frame N [--shot-exit]`（**应用自截屏**：与合成器无关，见下）
      `--audio FILE|off` `--autoplay` `--audio-offset-ms F`（音频见下一节）

工作区排布方案见 [`WORKSPACE.md`](./WORKSPACE.md)；**agent 编辑入口见 [`AGENT-API.md`](./AGENT-API.md)**。

## 事件重叠检测与冲突浏览器

事件重叠（同一轨道上两段同时覆盖一段时间）会破坏"无空隙不重叠"的轨道不变量，所以：

**检测算法与"何时重算"都由 `EditCore` 拥有**（`EditCore::overlaps`）：
算法本身是纯函数（`cmd::overlaps` / `cmd::overlaps_of_line`），但**什么时候重算属于文档语义** ——
核心自己知道刚才动过哪条线，于是每次成功改动后按那条线增量刷新、结构变化（增删线/BPM）与
撤销/回滚/载入时全量重算。GUI 与 CLI 都只是**读**这份缓存：

| 前端 | 怎么读 |
|---|---|
| GUI | `EditCore::overlaps()` → 底栏红字 `⚠ N 处事件重叠`、冲突浏览器；`ui_stats.conflicts` 暴露这个数 |
| CLI | `opm-ctl --file F overlaps [--json]`（有重叠 → 退出码 4），或附着模式下 `{"op":"overlaps"}` |

**为什么不让两边各写一份**：早先 GUI 自己维护 `conflicts` 缓存 + "哪条线动过"的判断，
CLI 完全没有这个能力 —— 同一件事两套实现，迟早出现"GUI 说 3 处、CLI 说 2 处"。
现在只有一份缓存，**两侧的输出可以逐字比对**（`artifacts/conflict-browser.png` 与 `opm-ctl … overlaps`
列的是同一批 pointer/label）。
- **冲突浏览器**：冲突一出现就自动展开（关掉后不会自己弹回来），每条列出
  `线 #L · 轨道 · 事件 i→j 重叠 [起, 止) 拍`，**点一下跳到那里**（选中该线/轨道/事件 + 播放头定位到重叠起点）。

"头尾相接"（前一个止拍 == 后一个起拍）**不算重叠** —— 那正是格式要的样子；只有真的多覆盖了一段才报。

## 属性编辑器（右侧栏）

右侧栏是**编辑器**而不是只读检查器：判定线的名字/zOrder/isCover/线速、事件的起止拍与起止值及缓动、
音符的类型/拍/时长/laneX/alpha/假音符/speed/宽度/yOffset 都能改。
所有改动都走命令（`set_line` / `set_event` / `resize_event` / `set_note`）—— 文档数据只能由 EditCore 写，
编辑器发出的命令与 agent 用 `--attach` 发的是同一套；改完靠广播刷新，编辑器自己不缓存文档。
事件的头/尾改时间走 `resize_event`（会同步邻块），值/缓动走 `set_event`。

### 输入时机：**只在回车 / 失焦时提交**（用户要求）

数值与文本字段都**不**在每次输入时写回文档。理由是踩出来的：检查器每次广播都重建，
若每敲一个键就发命令，重建会把快照里的**旧值**写回控件 —— 你敲 "12"，第一个字符就被冲掉，
字段变成 "1"、再敲变 "11"，数值输入根本没法用。

- 数值字段一律走 `inspector::value_field`：`DragValue::update_while_editing(false)`
  （egui 文档：值只在**回车或失焦**时更新，Esc 取消）。**鼠标拖动仍然实时** —— 拖就是在调值。
- 文本字段走 `inspector::text_field`：编辑期间那份文本放在 egui 临时内存里，**不用每帧重建的快照
  覆盖它**；提交同样只在失焦（回车、Tab、点到别处）那一帧。没在编辑时永远显示文档里的值，
  于是撤销/外部改动照常立刻反映出来。
- **判据不是 `Response::changed()`**（第二个踩出来的坑）：编辑态下 `DragValue` 返回的是**内部
  TextEdit** 的响应，敲第一个字符那一帧它就是真、而值纹丝不动。拿它当"该发命令了"的判据，
  打字期间会发一串**旧值**命令、把撤销栈灌满。`value_field` 因此返回**"值真的变了没有"**：
  打字期间不变（不发）、回车那一下变了（发一次）、拖动每帧都变（照旧实时）。

单测 `inspector::tests::value_fields_commit_only_on_enter` 真的驱动一遍控件：点进字段、敲三个字符、
断言期间一次都没提交、回车才变成 123，并同时钉住"存在'值没变但 Response 说变了'的帧"这一事实。

### 缓动的选法：**曲线 + in/out/io 两段**（用户要求）

不再在一串 29 个名字里翻，而是两个下拉：**曲线**（线性 / 正弦 / 二次 / 三次 / 四次 / 五次 / 指数 /
圆形 / 回拉 / 弹性 / 弹跳）× **变体**（`in` / `out` / `io`）。这不是"另一种排版"，而是**同一个集合的
另一种坐标**：RPE 的 29 个名字本来就是"曲线 × 变体"的笛卡尔积加一个 `linear`。

- 拆与拼在库里（`cmd::split_easing` / `cmd::easing_name`），有**往返测试逐个钉住 29 个名字**
  （拆开再拼回来必须一模一样），以及"下拉里所有格子拼出来的名字**正好等于** `EASINGS`"这条集合断言。
- **线性那一格没有变体**：第二个下拉**置灰**而不是藏起来 —— 布局不跳，"为什么没得选"也看得出来。
- **`quint` / `expo` 没有 `io`**（RPE 的 29 个里就没有 `inOutQuint` / `inOutExpo`），
  所以下拉里也不出现那两格；"切到 quint 时变体还停在 io"由 `EaseCurve::clamp_variant` 夹到 `out`
  —— 夹取规则只有一份实现，界面与 `easing_name` 都用它。
- **认不出的缓动**（老文件里的怪名字）：原样显示 + 一句"无法识别，已原样保留"，**不拿一个猜的名字
  去改用户的文件**。

证据：`artifacts/easing-two-part.png`（`inOutBack` 显示为 `回拉 back` + `io`；同一个谱面的 `linear`
事件在第二张里显示为 `线性` + 置灰的 `out`）。

## 数据边界：谁有权写谱面

一条硬规则（用户定）：**EditCore 只管最终会写进谱面文件的数据；这类数据的"写"只能发生在核心内部。**
界面自己的规则（网格吸附、播放头、选区、叠加层、线长…）与文件无关，界面自己管。

| 类别 | 例子 | 谁能改 |
|---|---|---|
| **文档数据**（会进 `.opm` 文件） | 判定线、事件轨道、音符坐标/类型、`meta.*`、BPM 表 | **只有 EditCore**（外部一律发命令：`exec` / `--attach` / GUI 控件 → 命令） |
| 界面视图状态（不进文件） | 播放头、播放状态、选区、网格与吸附、可见拍数、叠加层暗度、判定线**半长**、音频预览路径、音频校准 | GUI 自己，想怎么改就怎么改 |

**这条规则由编译器兜住**：`EditCore::doc` 是**私有字段**，外部只能 `doc()` 读到 `&Document`，
拿不到 `&mut`。想改文档就得写一条命令 —— 没有第二条路。早先有两处"绕过核心直接写文档"的飞地
（GUI 的演示谱面引导构建、`opm-ctl new` 的元信息/BPM）已经改为发命令；实测两者产出的文档
**逐字段完全一致**（449 条命令 0.01 s）。

音频是这条规则的好例子（两条路刻意分开）：

```sh
opm-ctl --attach auto --cmd '{"op":"audio","path":"preview.ogg"}'      # 只换预览用的音频（视图，不动文档）
opm-ctl --attach auto --cmd '{"op":"set_meta","set":{"audio":"song.ogg"}}'  # 改文档里的 meta.audio（会广播、可撤销、会写进文件）
```

实测：换预览音频后 `dump` 里的 `meta.audio` 不变；改 `meta.audio` 会广播（话题 `Meta`）且可撤销；
撤销文档字段**不影响**正在预览的音频。

`tests/boundary.rs` 把这三条钉住：文档核心不认识视图命令（`play`/`nudge`/`ui_stats` 一律 `ok:false`）、
音频两条路径互不干扰、**改一圈视图状态后文档逐字节不变且 revision 不动**。

## 编辑功能：判定线是父对象，音符是它的子对象

依赖方向是**单向**的，且体现在视图模型里（`src/state.rs`）：

```text
Document
  └─ judgeLines[]            ← 父对象：位置/旋转/透明度/流速全部来自它的事件轨道
       ├─ layers[] → 事件轨道（moveX / moveY / rotate / alpha / speed）
       └─ notes[]            ← 子对象：只存"线本地坐标"，屏幕位置由父对象的表演变换决定
```

因此左侧面板是四级层级，正好对应数据的依赖方向：

```text
判定线（4 条；doc 4 行 400 音符）
 ▶#0 L0 z0C ♪100 ⚡10 x-400 y0 r0 a1.0     ← 行尾就是该线**此刻**的表演值
  #1 L1 z1C ♪100 ⚡10 x0 y250 r0 a1.0
事件轨道（线 #0 L0）
 ▶moveX   2条 t=-400.0 [-400,400] RPE
  rotate  2条 t=0.0    [0,0] 度
事件（alpha 共 2 条）      [在播放头切分] [删除选中]
   0   0.00s    1.0→1.0   linear
子音符（100 个；线速 10.0）
   0   0.000s  -480.0  Tap
```

- **事件是"表演"的本体**：线在某一时刻的 x/y/旋转/透明度/流速 = 五条轨道在该时刻的求值结果
  （`src/perf.rs`：拍↔秒分段映射 + 29 个具名缓动的函数本体 + 事件求值）。缓动是真的参与求值，不是线性近似：
  同一段 `0→90°` 在动画中点，`linear` 给 45°，`outCubic` 给 **78.75°**。
- **音符跟着线走**：渲染时线和它的子音符走**同一个**变换（先旋转再平移），
  所以线一转，子音符的位置与倾角一起转；线与音符的实例化在着色器里用同一个 `angle`。
- 命令语言里 `line` 选的就是这个父对象（`{"op":"add_note","line":2,...}` 把音符加到 2 号线上）。

## 顶栏、设置与网格

顶栏只放**真设置**，不放调试开关（调试留在 CLI）：

顶栏是**两行**（工具多了单行会挤成一条看不清）。实测形态：

```text
OpenPhM | ▶ 播放 | ⏮ | demo-400 ♪ 400 | 📂 文件…
网格 拍 每拍 4 条 | 坐标 窗口 16 等分 | 可见 8 拍 | 窗口 X 偏移 0 RPE | ⟲ | 显示 0…1350 | 设置 ⚙
```

第一行 = 身份/传输/谱面摘要/文件入口；第二行 = 视图与网格设置（第二行用 `horizontal_wrapped`，
窗口再窄也会自己折行，不会把控件顶出去）。

| 元素 | 说明 |
|---|---|
| ▶ 播放 / ⏮ | 播放暂停（空格）、回到开头 |
| `demo-400 ♪ 400` | 曲名（`meta.name`）与音符总数 —— **只在广播后刷新的缓存**，不直接读文档 |
| 📂 文件… | 打开「文件」对话框（打开 / 保存 / 另存为 / 在文件管理器中显示）。**顶栏刻意不放保存按钮**（用户要求）：保存只从对话框或 `Ctrl+S` 走 |
| 网格 `拍 每拍 N 条` | 拍方向网格：步长 `1/N` 拍（纵向节拍刻度） |
| 网格 `坐标 窗口 N 等分` | 坐标方向网格：**整个可见窗口平均切成 N 列**，步长 `1350/N` RPE 单位（横向坐标刻度）。奇偶都可以（1..=128） |
| 第二行 `可见 N 拍` | 时间轴缩放（与编辑区 **Ctrl+滚轮** 同一条状态） |
| 第二行 `窗口 X 偏移` + `⟲` | **音符区显示的 laneX 区间整体平移**（`[偏移−675, 偏移+675]`，夹 ±675）；`⟲` 归零。右侧 `显示 a…b` 提示当前区间（非零时显示） |
| 设置 ⚙ | 编辑区叠加层（开关/暗度）、窗口边界框、判定线半长、命令控制台、校验谱面、工作区切换 |

**底部状态栏**（从左到右）：播放头 `0.000s / 0.00 拍` · `▶ 播放中` · `♪ 歌名`（欠载计数、校准偏移）
· 网格与步长 · **文档标识** · 窗口偏移 · 编辑区隐藏提示 · 冲突计数 · `⏳ 等广播`。

文档标识那一格是把"我在编辑哪份文件、存过没有"写得能直接读懂（而不是让人去猜一个圆点的意思）：

```text
[opm 容器] demo-400.opm   ● 有未保存改动      ← 改过之后（琥珀色）
[opm 容器] demo-400.opm   ✓ 已保存            ← 存过、且之后没再动（绿色）
[RPE] （未命名）          尚未保存             ← 还没有保存目标
```

悬停有完整信息：有目标时给出完整路径，没目标时明说"第一次保存会弹系统保存窗口让你指定路径"。
它由 `App::refresh_file_badge()` 在**事件上**重算（换文件、存盘、文档被改动），
不是在帧里锁核心 + 解析路径 —— 见「表现层也不许每帧白做工」。

**两个方向的步长互不相干**：横向步长只由「窗口 N 等分」决定（= 1350/N），纵向（拍）只由「每拍 N 条」决定。
代码里唯一的 `4` 是**小节线**（每 4 拍一条略强的线，纵向），它只是刻度、不参与吸附，**也不是基准**。
「窗口 N 等分」是**整窗平均切割**（边界对齐）：格点 = `-675 + k·(1350/N)`，k = 0..N，
所以两端恒为窗口边界（±675）、**任何 N 都放得下**，奇数不再被拒。
代价是**奇数 N 时 laneX = 0 不是格点**（吸附不落在中轴上）—— 但**中轴照画**：
它是"窗口正中"的视觉参考，由 `overlay` 单独画一条（偶数 N 时它本身就是第 N/2 条格线）。
格点是否含中轴由 `GridCfg::center_is_lattice()` 判定，有单测。
（历史上曾因"以 0 为中心"的格点在奇数下最外一条落到 ±810 而**只允许偶数等分**；用户否掉了这个限制。）

**线怎么画：以一拍为基准**。三档里**每拍线是正线**（1.5px、α170）—— 结构读起来是"一拍一格"；
4 拍小节只比它略强一点（2.2px、α215）用来定位，**不是**基准；1/div 细分线是细节（0.9px、α110），
**细但看得见**（用户要求"最细的线也画明显"；纵向坐标分格线同色同宽，两个方向的"最细档"是同一档东西）。
纵轴轴带里**每一拍补一个小刻度**（标注位置的更长，压在上面），所以节奏基元在轴上是看得见的：
实测轴带内缘亮段，改前 16 处 / 平均 46.3px（= 每 2 拍，只有标注位），改后 **32 处 / 平均 23.1px = 正好一拍**
（32 拍可见时一拍 ≈ 23.1px）。对比图 `artifacts/beat-base.png`。

**网格线就是吸附目标**：线画在哪、吸附到哪，用的是**同一个数** —— `EditorState::effective_beat_div()`
（`overlay::beat_grid_lines` 画线、`snap_beat`/`beat_json` 吸附，全部读它）。**整拍线在抽稀时永不跳过**。

**为什么会有"实际 1/N"**：可见拍数很少时 1/16 网格的线距不到 1px，画出来就是一片糊，
所以设定值会被顶到"当前缩放下画得出来的最大约数"（`GRID_MIN_LINE_PX = 1.2`，约数 ⇒ 永远是 1/2、1/4、1/8 这类整齐步长）。
关键是**吸附跟着一起降**，否则用户会看到两个毛病（都实测过）：
①把每拍条数从 4 调到 8/16 画面毫无变化（细线被另一套规则静默抽稀）；
②吸附落在**没画出来的线**上（"吸附不遵循规范"）。被顶掉时顶栏与状态栏会明写 `→ 实际 1/8`
（顶栏琥珀色提示，状态栏 `每拍 32 条(实际 1/8)`），放大（缩小可见拍数）即可启用更细的网格 ——
它不是永久禁用。单测 `drawn_grid_equals_snap_grid_and_responds_to_setting` 把"画线数随设定变化 + 吸附结果必定是画出来的线（双向）"钉死。

两个方向各一个数（取代了原来的两个吸附勾选框）。**音符拖拽与双击放置总是落在两轴网格的交叉点上** ——
界面上不存在"格点之间的音符"（自由坐标仍可走命令给 agent 用）。这既是"可指定的格点集"，
也保证写回文档的拍是**有理数 k/N**，而不是浮点抖出来的 0.3333333（`GridCfg::beat_json`）。

**调试信息去哪了**：`压力模式`、帧时间/实例数/广播重建计数、适配器这些只在**调试工作区**（`--ws debug`）
或 CLI 里出现（`--stress`、`--verify-align`、`ui_stats`、`--verbose-updates`）。顶栏与状态栏平时只有
播放头、音频、网格/吸附、编辑区状态。

## 编辑区（叠加在预览上的拍空间编辑器）

演奏区是"游戏里会变成什么样"的唯一视图，而编辑要盯着数据 —— 所以编辑区**叠在预览上**，
半透明，两边同时可见；不编辑时按 `H`（或一开始播放）就藏起来，预览立刻干净。

```text
┌─────────────────────────── play_rect ───────────────────────────┐
│（顶上窄行：编辑区标题 · 右半的轨道列名 moveX…speed）             │
├──────────────────────┬─────────┬───────────────────────────────┤
│ 音符轨道区            │ 纵轴     │ 事件区（当前判定线 5 条轨道）  │
│ x = laneX（±675 铺满）│ 拍号写在 │ x = 轨道列                    │
│ y = 拍（越上越晚）    │ 轴带里， │ y = 拍；事件 = 起止拍之间的块 │
│ Hold 竖条 / 假音符空心│ 两区分开 │ 块内标起止值与缓动名          │
└──────────────────────┴─────────┴───────────────────────────────┘
```

拖拽的判定按**按下时**指针的位置算，而不是"当前指针位置"：egui 要等指针移动几个像素才认定为拖拽，
那时指针已经离开 6px 的把手段了（这是"有提示但拖不动"的一个成因）。

**纵轴在中间**（不是贴左边缘）：它是两个区**共用**的纵轴。轴带宽 34px，拍号居中写在里面、
两侧各一个小刻度线指向相邻半区，两半的网格线在轴带边缘停住 —— 视觉上就是"被轴隔开的两个区"。
点在轴带上不会选中任何东西（轴是骨架，不是内容）。

- **纵轴是拍**，不是秒 —— 编谱时想的是"第 32 拍"，不是"第 10.67 秒"。
  **可见拍数默认 8 拍**（`EditorState::DEFAULT_OVERLAY_BEATS`；用户要求"时间轴拉长 4 倍"，原来是 32 拍）：
  一拍 ≈ 75px，1/4 拍细分线 ≈ 19px、1/16 拍 ≈ 4.7px —— 最细的线只有在放得足够大时才真的有意义。
  设置里可拖、可 Ctrl+滚轮，CLI `--overlay-beats N` / `{"op":"zoom",...}`。
- **纵轴数字标注的密度与精度随缩放变**（`overlay::axis_ticks`）：网格多密由设置（每拍 N 条）决定，
  标注多密由"放不放得下字"决定（`AXIS_LABEL_MIN_PX = 34`）。步长只走 4·2^k 阶梯（… 1/4、1/2、1、2、4、8 …），
  精度由步长定：4 拍可见 → 每 1/4 拍一条、两位小数（`0.25` `1.50`）；32 拍可见 → 每 2 拍、整数；
  256 拍可见 → 每 16 拍、整数。实测截图见 `artifacts/zoom-labels.png`。
- 纵轴画在**中间**（两区之间），拍号写在轴带里；见上面的布局图。
- 跟随播放头：窗口是 `[播放头 − 2 拍, +30 拍)`，暂停在哪就停在哪。
- 左半与右半都是**当前判定线**的：线是父对象，音符和事件都是它的子数据（与左侧判定线树同一个模型）。
- 交互：
  - **滚轮** = 改当前时间（向上滚 = 往后；步长随可见拍数缩放，32 拍可见时一格 2 拍）；
  - **Ctrl + 滚轮** = **缩放时间轴**（向上滚放大、可见拍数变少；等比，三格大致翻倍/减半，
    范围 4～256 拍）。注意这不是从 `smooth_scroll_delta` 拿的：egui 0.36 一旦发现 `wheel.modifiers`
    命中 `options.zoom_modifier`，就**不把滚动写进 `smooth_scroll_delta`**，而是折算成 `zoom_delta`
    （`exp(scroll_zoom_speed · Δ)`）—— 按住 Ctrl 时读 `smooth_scroll_delta` 会恒为 0（无头测试实测）。
    缩放是**纯视图状态**：谱面文件里没有"可见拍数"这个字段；
  - **拖动音符块** = 移动（横向改 `laneX`、纵向改拍，**总是**落到两轴网格的交叉点；Hold 保持时长一起挪）；
  - **对准事件块的头/尾拖**（起点在**下方**、终点在上方；两侧 6px 内，光标进入时对应那条边会亮，
    **指针变为上下双头箭头**）= 调事件的起止时间，按拍网格吸附。**控制柄只控制它所属的那一个事件**：
    不碰邻居（早先会"同步邻块以维持无空隙"，那会让一次拖拽同时改两个事件 —— 已被否掉）。
    拖出的**空隙/重叠**由检测机制报（重叠进冲突浏览器与底栏红字，空隙进 `validate`）。
    事件块**整块带渐变**，方向是**色相偏移**（起点在下、终点在上，色相转 40°，**透明度与明度两端相同**）——
    不用"变暗/变透明"做渐变，那样叠在深色预览上会糊。选中态只是整体更实一点，两端仍然一致。
  - **头尾相接处抓谁**：优先**选中的**那个事件；两个都没选中时抓**尾巴**（即"止于这一点"的前一个事件）。
    这条规则由 `overlay::prefer_edge` 决定，有单测。
    **把手高亮与拖拽共用同一个决策**（`overlay::handle_to_highlight`）—— 头尾相接时 A 的上边与 B 的下边
    落在同一条 y 上，若两边各自判定会出现"两个把手同时亮、像一次选中了两个"，所以只允许一处决策。
    （早先为"保持轨道无空隙"会在拖动时同步邻块，那等于一次拖拽改两个事件；现在邻块一律不碰，
    拖出的边界由重叠检测兜住 —— 语义与实测见下）；
  - **双击空白** = 在该格放一个 Tap（同样吸附）；
  - 单击选中音符 / 点事件列切换轨道 / 点事件块选中事件 / 点标尺把播放头定位到那一拍。

### 多选：框选 / Ctrl 点选 / 整组拖动 / Del

| 手势 | 做什么 |
|---|---|
| **点击**音符或事件块 | 选中它一个（替换整个选区）；点空白/轴带**清空**选区 |
| **Ctrl + 左键** | 把点到的那个在**选中 / 未选中**之间切换（多选的主要入口） |
| **Shift + 左键拖动** | **框选**：碰到框的就算选中（矩形相交）。空框 = 清空 |
| **在多选上按住拖动** | **整组平移**：音符走 X 与拍两轴，事件只走时间轴；相对间隔完全保持 |
| **Del** | 删掉整个选区（音符或事件），**一个撤销步**（`Ctrl+Z` 一次全回来） |

四条规则各有出处，写下来免得下次又猜：

1. **选区同时只有一类**（音符 xor 事件）。框选跨过两区时**以拖动起始点落在哪个半区决定选哪一类**
   （用户定的规则；起始点取 `pointer.press_origin()`，不是"刚判定为拖拽"那一刻的指针 ——
   后者已经被拖拽阈值带跑了，会按错半区）。Ctrl+左键点到另一半区时把旧的清掉。
2. **锚与集合是两件事**：`selected_note` / `selected_event` 是**锚**（每一类最后碰过的那一个），
   检查器、判定线树、时间轴高亮都只认锚 —— 所以"点了音符"不会顺手把事件编辑器收起来
   （老的界面两边同时显示，没理由退化）。Del 与拖动作用的是**集合**。
3. **抓手（`edit::Grab`）在按下那一刻冻结**：成员、原点、手指位置全部记下来。拖拽期间文档每帧都在变，
   若每帧从文档反推"它原来在哪"，位移会逐帧累积 —— 表现就是"拖一下跑得比鼠标还快"。
   整段拖拽仍然是一个撤销步（`begin` → 逐帧 `set_*` → `commit`），逐条改动照常广播。
4. **事件的"最近合法位置"（kdenlive 式）**：事件的轨道是要**无缝铺满时间轴**的，所以"整块平移"必须
   回答"能与谁重叠"。规则是：请求的位移若会让选中块与**未选中的**邻居重叠，就退到**离请求最近的那个
   合法位置** —— 于是
   - 指针拖得不够远 ⇒ **贴住邻居边界就停**（相接不算重叠）；
   - 指针**拖得够远、越过了障碍** ⇒ 整块**跳到障碍另一侧的空档里**（这正是 kdenlive 的时间轴行为）；
   - 轨道整条铺满、又没有空档 ⇒ 唯一的合法位置是原地（"夹住"的字面结果）。
   实现在 `edit::nearest_free_delta`（纯函数，有单测）：把"会重叠的位移区间"并起来，
   再在补集里取离请求最近的点；下界是"不许挪到负拍"。
   **音符没有这个问题**（音符之间本来就可以重叠），所以只受"负拍"和"看得见的窗口"约束 ——
   整组按极值一起夹，不逐条夹（逐条夹会把相对间隔压扁）。
5. **选中了卷进重叠的事件 ⇒ 直接禁止移动**（用户要求）。重叠意味着这条轨道已经不是"一块接一块"的结构，
   "挪到最近合法位置"那套推理整个失去意义 —— 与其猜一个位置，不如拒绝并说清楚：
   *拖它的头/尾把手指时间，或到冲突浏览器里点过去处理*（**改时间那条路仍然可用**，那才是修重叠的正道）。
   判据是 `edit::event_items_overlap`：**两两比较**，不是"排序后看相邻的一对"
   —— [0,10) / [1,2) / [3,4) 里第三块和第二块相邻、和**第一块**才重叠，只查相邻会漏；
   **相接不算重叠**。悬停时该事件的**块体**光标直接是"禁止"、按下去不开事务（只给一句话）；
   **头/尾把手不在禁用之列** —— 拖把手改时间正是修重叠的那条路。

**光标就是"拖起来会怎么动"**：多选里的音符悬停 → **四向箭头**（X 与拍都能动）；多选里的事件、
以及任何事件块本体/把手 → **上下双头箭头**（事件只有时间一个轴）。单选/未选中的音符仍是抓手。

**多选之后"选了几个"必须一眼可见**：所有成员都描边（锚用实线白框、其余成员稍细的浅框），
编辑区标题下面一行写"已选 N 个音符 / N 条事件 · Del 删除 · 拖动…"。框选的框是实时画的矩形
（音符区蓝、事件区橙）。

**Del 是全局键**（不吃"指针要在编辑区上"）：作用在选区上，门槛与 `Ctrl+Z` 一致
（在文本框里打字、模态开着时不吃）。删除顺序是**正确性的一部分**：`del_note` / `del_event` 都是
`remove(index)`，删掉第 3 条之后原来的第 4 条就变成第 3 条 ⇒ **同一张表里必须按下标降序发**
（`edit::delete_selection_commands`，有单测钉住顺序）。

**事件一律按"文档地址"改**（`doc::EventRef` = 第几层 + 该层事件表里的下标）。视图把一条线的
**五个图层合并**成一条时间线（求值要的就是这个），合并序号与任何单独图层里的序号都不是一回事 ——
拿合并序号去 `del_event`，在多层文档上删掉的是**另一条事件**。渲染/求值仍按合并顺序，编辑走地址。

### 快速放置的键位（Q/W/E/R）与半区

音符区：`Q`=Tap、`W`=Flick、`E`=Drag、`R`=Hold（Hold 进入跟随鼠标的草稿态）。
**事件区只认 `R`**（起一个事件块草稿，与 hold 同一套跟随流程）—— `Q/W/E` 在事件区**没有任何反应**。
规则在 `overlay::quick_key_rule`（纯函数，有单测）：这四个键只对音符有意义，早先拿它们去起事件草稿
是误触（用户报的）。指针不在任何一个半区里（标尺/轴带上）时给一句说明，而不是静默。


- **窗口 X 偏移（编辑窗口外的音符）**：官方窗口是 laneX ∈ ±675，但"越界坐标"在格式里**是合法的**
  （`validate` 只报**警告**"超出 RPE 坐标系 ±675"）。顶栏第二行 `窗口 X 偏移` 把音符区显示的区间平移到
  `[偏移−675, 偏移+675]`（夹 ±675，所以最多能看/改到 laneX ∈ ±1350）。要点：
  - **格点锚在官方坐标系上**（`−675 + k·(1350/N)`）并**向两侧延伸**，所以平移之后照样"吸附就是格点"，
    只是可以吸到窗口外（偏移 0 时吸附仍然永远落在 ±675 内，行为跟以前一模一样）；
  - **中轴（laneX=0）持续画**；**官方窗口边界 ±675** 用**橙色竖线**标出来 —— 平移后一眼能看出
    "橙线右边/左边就是窗口外"；
  - 窗口外的音符被**裁到音符区**内绘制（否则平移后它们会糊到轴带/事件区上）；
  - 只影响编辑区怎么显示与吸附，**演奏区预览永远显示真实窗口**；
  - 它是**视图状态**（文档里没有这个字段），CLI 等价：`--window-offset X` / `{"op":"window","offsetX":X}`。
- 叠加层和判定线树一样**只产出动作**，由调用方施加 —— 界面不直接改数据。
- 事件头/尾用 `{"op":"resize_event","line":L,"layer":0,"track":T,"index":i,"edge":"start|end","toBeat":[n,d]}`：
  **只改这一个事件**（越界"把自己的头拖过自己的尾"会被拒）。
- "如果某时间没有事件则不移动判定线"落在**求值器**上：事件之间有空隙时，那条线的值**保持前一条事件的终值**，
  不会跳到别处（`perf::eval_events`）。这里修过一个真 bug：早先落在空隙里会返回"最后一条事件的终值"，
  于是线在空隙中直接跳变 —— 那才是"判定线自己动了"。
- **整段拖拽 = 一个撤销步**：拖动时发 `begin`，逐帧发 `set_note`，松手发 `commit`；
  而每条改动**仍然逐条广播**，所以拖动过程中面板是实时更新的（这两件事此前被绑在一起，见"更新广播"一节）。
- 滚轮与拖动都有等价的 CLI 形态，因此可被脚本验证：`{"op":"nudge","beats":2}`、
  `begin` → 多次 `set_note` → `commit`（实测：拖 3 帧 = 3 条广播、撤销 +1 步、文档里是 `11/4` 拍这种精确有理数）。
- 可见性规则：`enabled && !playing && !h_held`（抽成纯函数 `overlay::overlay_visible`，有单测钉着）。

| 控制 | 位置 |
|---|---|
| 显示/隐藏整个编辑区 | 工具栏 `编辑区` 勾选框；`--overlay on|off` |
| 线档位（基准 = 一拍） | 每拍线 1.5px α170（正线）· 小节线 2.2px α215（略强）· 细分线 0.9px α110（细节但看得见）· 坐标分格线 0.9px α110 / 中线 1.3px α160；轴带每拍一个短刻度 |
| 可见拍数（缩放） | **Ctrl+滚轮**（编辑区内）；工具栏 `可见 N 拍`；`--overlay-beats N`；CLI `{"op":"zoom","beats":N}` / `{"op":"zoom","factor":F}` |
| 底板黑度（数据清晰度 vs 预览可见性） | 工具栏 `暗度` 拖动框（默认 **0.82**，越大越黑）；`--overlay-alpha F` |
| 临时隐藏 | **按住 H**（放开即恢复；控制台输入时空格/H 都不触发） |
| 播放时 | 自动隐藏（`ui_stats.overlay_visible` 可观察） |

无头出图（`render`）**不含**编辑区 —— 给 agent 的图里不该有编辑器 chrome。
实测（截图：`artifacts/edit-overlay.png` 暂停态 / `artifacts/edit-overlay-hidden.png` 播放态）：
暂停时 `overlay_visible=true`，播放中 `false`，再暂停 `true`；
`{"op":"nudge","beats":N}` 全部精确落位（+2→18.00 拍、−4→14.00、10×+1→24.00、往前滚过头停在 0 拍）。

滚轮事件无法注入 Wayland 窗口（xdotool 需要 `DISPLAY`），所以换算抽成纯函数单测
（`scroll_delta_to_beats`、`zoom_delta_to_beats_factor`、`axis_label_step`），
**施加路径**分别用等价的 `{"op":"nudge"}` / `{"op":"zoom"}` 端到端验证 —— 同一份代码。
缩放那条还额外用**无头 egui 合成滚轮事件**走了一遍（`ctrl_wheel_zooms_while_plain_wheel_seeks`）：
不按 Ctrl 只出 `ScrollBeats`，按住 Ctrl 只出 `ZoomBeats` —— 这条测试抓出的正是"ctrl 时读 scroll 恒为 0"。

## 保存与加载（opm 原生 + RPE）

**两种格式都是 `.json`，一律按内容判格式**（不看扩展名）：有 `format: "opm"` 的是 opm；
有 `judgeLineList`/`BPMList` 的是 RPE。读取路径只有一条：`EditCore::load` → `codec::to_document`。

### 启动顺序：先解决"选哪份谱面"，再进编辑页

打开程序**不会**直接给你一个编辑器（也不会拿一份内建演示谱面糊上去），而是先在**自己的窗口**里选谱面；
启动页上的问题（缺 7z、新建谱面的表单）都是**盖在它上面的模态**，不是另外的整屏。

| 阶段 | 窗口标题 / 尺寸 | 内容 |
|---|---|---|
| 选择谱面 | `OpenPhM — 选择谱面`（尺寸与编辑页**相同**） | 左＝最近打开，右＝打开…/新建…/跳过。缺 7z 时标题变成 `OpenPhM — 缺少 7-Zip`，并盖一层门槛模态 |
| 编辑页 | `OpenPhM — <曲名>（<文件名>）`（`--width/--height`） | 编辑器本体 |

- **编辑页不再内建任何演示谱面**：没选文件就进来（`跳过`）得到的是**空的未命名谱面**（♪ 0）。
  需要压测/造图时显式给 `--notes N` —— 实现在库里 `opm_app::demo::build_demo_via_core`，
  **走命令路径**（不是直接构造文档），GUI 的 `--notes` 与 CLI 的 `opm-ctl new --demo-notes N` 共用同一份。
- **「新建谱面」是启动页上的一个模态**（用户要求"不要直接切换整个界面"）：盖在谱面列表上，
  窗外尺寸不变、标题不变；Esc / 点遮罩 = 返回列表（**不是**跳过进编辑器 —— 人在填表，
  别把他踢进编辑器）。填表 → 校验（曲名必填、BPM 为正）→ 创建 → 进编辑页。
  编辑页里的「新建…」仍会**切回启动页**（谱面的建立只发生在那里；有未保存改动时先过守卫）。
  表单校验与提交参数在 `recents::NewChartForm`（有单测），不在 GUI 里各写一份。
- **所有弹窗只有一套外观**（`dialog` 模块）：文件对话框 / 未保存守卫 / 新建谱面 / 缺少 7z
  用的是同一个 `egui::Modal` 底板、同一族宽度（480 / 560 / 660）、同一套提示色、同一种关法。
  **Esc 的归属也在那里收口**：`ModalResponse::should_close()` 会**消费掉** Esc，所以弹窗开着时
  底下的界面（列表的"跳过"、编辑页的快捷键）看不到它 —— 有单测钉住"一份 Esc 只产生一个动作"。
- `--doc FILE` 直接进编辑页（CLI / agent / 截图都走这条），不经过启动页。
- 自动化钩子：`OPM_LAUNCH_AUTO=skip|new|create:<曲名>|open:<path>|recent:<n>` 让启动页自己做出选择 ——
  没人点鼠标时也能把"选完切编辑页"这一段走完（截图与 CI 用）。**缺 7z 时这些钩子一律不生效**，
  否则 `skip` 就成了绕过 7z 检查的后门。
- 自动化钩子 `OPM_CLOSE_AUTO=<帧号>`：在第 N 帧**模拟点右上角的叉**（发一个 `Close` 请求）——
  "未保存就退出"的守卫本来没法自动验（往 Wayland 窗口注入点击这条路在本会话是断的），
  有了它，守卫拦没拦住就是一个可复现的观察：进程该活着还是该退出，直接看退出码。
- `--shot` 的决策是纯函数 `shot::shot_step`（有单测）：**没给 `--shot` 时永远什么都不做**。
  这条不是洁癖 —— 曾经因为抽方法时漏掉这个守卫，默认第 30 帧会发一次截图请求、
  下一帧对 `None` 做 `unwrap()`：鼠标在启动页一动就疯狂重绘、30 帧几秒就到，于是"一移动就崩"。
- **关于"独立窗口"的取舍（实测约束）**：eframe 里**只有根视口跑 pass**（子视口都在根的 pass 里绘制），
  关掉根 = 退出、隐藏根 = 完全不跑 pass。所以"启动窗口关掉、编辑窗口留下"这套在 eframe 里做不到；
  现在是**同一个窗口的两个页面**：标题不同、**尺寸相同** —— 来回切换**不发 `InnerSize`**，窗口不会跳（用户要求）。
  真要两个并存窗口，得换自管 winit 多窗口，或让启动窗口常驻。

**GUI 的文件入口是一个对话框**（顶栏「📂 文件…」；`--dialog file|new|guard` 可让启动时就摊开某个对话框，
供截图/人工检查；其中 `new` 是启动页上的那个模态，会顺带把阶段拨回启动页）。
**顶栏不放保存按钮**：保存只从对话框或 `Ctrl+S` 走。对话框里的「保存目标」是**只读显示**（用户要求）—— 目标的真值只在 `EditCore` 里，想换地方只有「另存为…」或第一次保存时的自动弹窗，不存在「框里手打」与「系统框里选」两套并行口径。

```text
文件
保存目标  tests/data/messy.rpe.json          ← 文件夹 + 谱面名字合成**一个**目标
格式 [rpe]  曲名 codec test  [应用曲名]
[🆕 新建…] [📂 打开…] [💾 保存] [⤓ 另存为…] [🗂 在文件管理器中显示]
另存为格式  自动 / opm / RPE
目标 [_______________________]  [采用此目标]   ← 直接写路径也行
```

**保存目标是一个东西**：文件夹与谱面名字合起来构成它，界面上就是一行路径；
没有目标时显示「（未指定 —— 保存时会弹保存窗口）」。
**曲名**（`meta.name`）是**文档字段**，与目标分开：它显示在顶栏、当另存为的默认文件名。
曲名不逐字生效（回车或「应用曲名」时才发一条 `set_meta`，逐字生效会灌满撤销栈）。

### 文件生命周期（Krita 那套）

| 动作 | 行为 |
|---|---|
| 🆕 **新建…** | 切回启动页并盖上"新建谱面"**模态**：**曲名 / 谱面作者 / 音乐作者 / 音乐路径（浏览…）/ 曲绘路径（浏览…）/ 基础 BPM**。创建后保存目标**清空**、撤销栈清空、文档**是脏的** |
| 新建/打开时**有未保存改动** | 弹三选一：**保存｜不保存｜返回**（少了"返回"就只能被迫二选一） |
| **保存**（`Ctrl+S` 或对话框按钮） | **有目标就写回它**（不弹任何窗口）；**没有目标才弹文件选择窗**（与「另存为…」同一条路） |
| **从文件加载** | 保存目标 = 那个文件，格式也跟着它（RPE 进就 RPE 出） |
| **关窗/退出** | 先过**未保存守卫**：有改动就弹「保存｜不保存｜返回」；干净直接退。走的是 eframe 官方否决式（`close_requested` + `CancelClose`），启动页与编辑页共用同一个守卫 |
| 另存为 | 系统文件对话框，**预填"存在的目录 + 曲名 + 扩展名"**（打包 → `.opm`/`.pez`，不打包 → 选目录）；选完没写扩展名会按形态补上 |

**时间轴总长 = max(乐曲时长, 最后一个 note/事件) + 10 拍**（用户给定的公式）：`EditorState::timeline_duration()` —— 只由**文档内容**与**乐曲时长**决定，**与播放头/滚动/缩放无关**（拖时间轴不会跳）。那 10 拍只是显示留白（否则最后一个音符贴右边缘），**绝不写进文件**（文档里没有「总长」这个字段，RPE 的 `chartTime` 取的也是内容末端）。公式的输入取自**文档**（`doc.chart_end()`，任何内容广播都刷新到 `EditorState::content_end_beat`）—— **不是**视图模型里的副本：那份只在 `structure` 变化时重建、加音符不重建，曾经因此出现「音符在 68.9s、时间轴还停在 20.0s」。打开谱面会重新装载它的音乐（`--audio` 仍优先、`--audio off` 明确不要）。

**读数里会写出公式的两个输入**（宽到放得下时）：`总长 63.4s（音乐 60.0s ｜ 内容 16.5s / 48 拍）｜ …` —— 「音乐 无音乐」就说明短的原因是音乐没装上，而不是总长公式；`OPM_TL_TRACE=1` 会在这两个输入或结果变化时打一行（`[tl] 总长 … = max(音乐 …, 内容 …) + 10 拍`）。

时间轴的实现整体在 `app/src/timeline.rs`（**独立模块**：几何与读数都是纯逻辑、可单测；`main.rs` 里只剩一次 `timeline::draw(...)` 调用）。

**时间轴上那两条标记**：**黄线 = 编辑区起点**（编辑区**底部**对应的时间 = 当前拍退回 `lead_beats`）；
**浅色带 = 编辑区可见跨度**（从底部到顶部，即再往上 `overlay_beats` 拍）；**播放头是那条细白线**
（在黄线上方 2 拍处，两者刻意画成两种东西）。左上角两行读数把它们写清楚；**窄窗口下这两行会按可用宽度逐级省略**（先丢右上角的「线 #N · 轨道 X」—— 左侧「事件轨道」那行本来就有；再缩图例、最后只留「总长」），判据是 `layout_no_wrap` **量出来的像素宽**，不是按字符数猜。宁可少一行，也不让读数撞字或被裁。几何都在
`EditorState::edit_area_span()` 里（与叠加层的 anchor 同一套定义），详见《框架选型》§7.56。

**脏状态（"需要保存"）只由 `EditCore` 维护**：接口就是 `is_dirty()` / `save()` / `save_as()`，
判据是内部两个版本号（`revision != saved_revision`）。任何**成功**的改动命令都在 `dispatch` 的
**同一处**把 `revision` +1（查询命令不动、失败的命令回滚后不动），所以"改了就要保存"是结构性的，
不靠各处自觉；GUI 里的 `file_dirty` 只是每帧取来显示的缓存。两条**故意**的保守口径：
撤回保存点之后仍算脏（宁可多提示一次）；`EditCore::new()` 的空占位文档算干净（否则刚启动点关窗会被问
"要先保存吗"）。细节见《框架选型》§7.51。

**音乐与曲绘都要进 `.opm`**（用户要求"音乐和曲绘都要放到 opm 文件中"）：表单里那两个"浏览…"
各自带**对应的文件过滤器**（音频 `ogg/mp3/wav/flac/m4a/aac/opus`；曲绘 `png/jpg/jpeg/webp/bmp`）——
以前这里复用了谱面过滤器，于是"选音乐"的系统框**只列 json 文件**（用户报的 bug）。
字段写进 `meta.audio` / `meta.background`，保存容器时由 `container::collect_assets` 读进来打包，
并把文档字段改写成**包内文件名**（可撤销）。映射与过滤器定义在库里（`recents::ASSET_PICKS`
+ `StartAction::asset()`），所以"哪个字段用哪个过滤器"有单测钉着，不再靠 `main.rs` 里肉眼接线。

**"保存新文件时无法指定路径"的修复**（用户报的问题，根因在系统框的起始位置）：
`kdialog --getsavefilename` 的第一个参数是 **startDir** —— 传进去的路径若不存在，
KDE 会把它当目录并报"目录不存在"，于是"新文件还没有对应文件"时反而指定不了路径。
现在起始位置一律过 `filedialog::nearest_existing_dir()`（向上退到最近的**已存在**目录），
所以"文件不存在"不再影响指定目标。另外两条同类修复：
- 目标目录不存在时给**能看懂**的错（`目标目录不存在：…（先建好目录，或用「选择文件夹…」）`），
  而不是内核那句 `No such file or directory`；
- 系统框返回的路径**没有扩展名就按格式补上**（opm → `.opm.json`，RPE → `.json`），与 Krita 同款。

### 系统对话框本身

打开…/另存为… 调的是**桌面自己的文件对话框**（本机实测 `kdialog` ✓ `zenity` ✓；Plasma 上就是 KDE 的框，
含覆盖确认、最近位置、书签)。探测顺序 `kdialog → zenity`，都没有时退回对话框里的「目标」输入框。
`🗂 在文件管理器中显示` = `dolphin --select`（退化 `xdg-open` 目录）。
系统对话框是**阻塞**的，所以所有动作都在 UI 之外执行；模态框打开期间空格/H 等快捷键被屏蔽。

| 入口 | 说明 |
|---|---|
| 快捷键 | `Ctrl+S` 保存（**没有保存目标时弹保存窗口**；有则写回，RPE 进 RPE 出）、`Ctrl+Shift+S` 系统另存为、`Ctrl+O` 系统打开、**`Ctrl+Z` 撤销 / `Ctrl+Shift+Z` 重做**（键位表在 `keymap::edit_shortcut`，有单测；在文本框里打字或模态打开时不吃这些键） |
| 命令行 | `opm-app --dialog file\|new\|guard`：启动就把对应对话框摊开（截图/人工检查用，不参与正常流程；`new` = 启动页上的新建模态） |
| CLI | `opm-ctl --file <opm 容器 / 裸 opm / RPE> …`（validate/summary/dump/render/lines 三种都吃） |
| 转换 | `opm-ctl convert IN [--to opm\|opm-dir\|rpe\|rpe-dir] [--out PATH] [--rpe-version N]` |
| 控制通道 | `{"op":"load","path":…}`、`{"op":"save"}`、`{"op":"save","path":…,"format":"auto\|opm\|rpe"}` |

**格式守恒**：RPE 进就 RPE 出。打开一个 RPE 谱面然后 `Ctrl+S`，写回去的还是 RPE ——
不会悄悄变成 opm。另存为按扩展名/目标名判：`.opm` → opm 包、`.pez` → RPE 包、目录 → 对应文件夹；**新建单文件 `.json` 会被拒绝**（保存形态只有那四种），但**已存在的**单文件依旧按原形态写回。

**保真度报告**：每次导入/导出都产出（CLI 打印、GUI 进控制台、`ui_stats` 里也有）。
报告分两栏：**做了什么转换**（信息）与**哪里降级了**（要人看）。同类问题会合并计数 ——
真实谱面里每条线都有 `extended`/`*Control`，逐条报会得到 34 行几乎一样的文字，把真正该看的淹掉。
有降级时 `convert` 的退出码是 **1**（与"用法错误" 2 区分开），脚本能发现。

**导入侧必须做的规范化**（否则产出的 opm 不合法，规范 §9 明列这是 codec 的职责）：
排序、丢零长度/倒挂事件、空隙按**前值延拓**补齐、重叠裁剪、
首事件补到拍 0、末事件延拓到谱面结束、`hold` 的 `endTime ≤ startTime` 补成 1/64 拍、
`BPMList` 空/首项不在拍 0 时补默认条目。

**已知降级**（报告里会写，别当成没发生）：
- `extended`（故事板）、`*Control`（按距线距离的控制曲线）、`father`（判定线嵌套）：
  opm v1 未建模，**原样保留在扩展袋**并在导出时写回，但预览按"独立线 + 忽略控制曲线"处理；
- RPE 负 alpha（"连音符一起隐藏"的废弃功能）→ 降为 0；
- `easingLeft/easingRight`（缓动区间裁剪）原样保留，预览按完整缓动曲线走；
- 多层事件（`eventLayers`）：分层结构与每层数据都保留，但**本机预览把多层合并成一条时间线求值**，
  与 RPE 的"逐层叠加"语义不同（`perf::track_events` 的历史简化）。

## 谱面容器 `.opm`（ZIP）与裸工程文件

**"opm 文件"的正式形态是 ZIP**：`chart.opm` 里装着谱面与资源，一个文件就能带走全部东西。

```text
chart.opm                ← ZIP
├─ opm.json              ← 谱面本体（与 .opm.json 完全同构）
├─ song.ogg              ← 音乐：条目名 = meta.audio
├─ bg.png                ← 曲绘/背景：条目名 = meta.background
└─ …                     ← 不认识的条目**原样保留**（不许悄悄丢）
```

| 形态 | 用途 | 打包方式 |
|---|---|---|
| `*.opm`（ZIP） | **分发**：一个文件带走谱面 + 音乐 + 曲绘 | **优先系统 `7z`**：谱面/文本 Deflate、音乐/图片 Copy 直存（对已压缩数据再压缩是白烧 CPU）；`-mtm/-mta/-mtc=off` ⇒ **同样输入同样字节**。没装 7z 时用内置实现（全 STORE） |
| `*.opm.json`（纯 JSON） | **工程文件**：可 diff、可入版本库、agent 与测试都用它 | 原生序列化 |

判格式**按内容**：ZIP 魔数 ⇒ 容器；否则当 JSON（裸 opm / RPE）。所以 `opm-ctl --file xxx` 三种都吃。

- **解包先走内置实现**（纯内存，覆盖 STORE/DEFLATE）；遇到 ZIP64/奇怪方法再交给 7z，并在报告里说明换了后端。
- **保存容器时会改写资源路径**：`meta.audio`/`meta.background` 若是外部绝对路径，会把文件读进包、
  并把字段改写成**包内相对名**（走 `setMeta`，**可撤销**）。读不到的文件只**报警告**，不静默产出缺音乐的包。
- **载入容器/谱面包时，整份内容摊到 `<临时目录>/opm/<内容 hash>/`**（Linux `/tmp/opm`、Windows `%TEMP%\opm`）：
  谱面本体写成 `opm.json`、资源逐个落盘，于是"按路径装载音乐"这条既有链路找得到它（`meta.audio`
  里写的是**包内文件名**）。条目名只取文件名，`../` 之类不会写到缓存目录外。
  这份缓存**一个进程至多留一份**（换谱面即删旧的那份，正常退出时删掉自己的那份），
  超出 **512 MB** 时按 mtime 从旧到新修剪（`/tmp` 常是 tmpfs ⇒ 摊出来的是内存）。详见下一节。
- 自己实现的 ZIP 只覆盖"够用且明确"的范围：**单文件 ≤ 4 GiB，STORE + DEFLATE**，不支持 ZIP64/加密/多卷 ——
  遇到就明确报错，不猜。（本机对 crates.io 不可达，加不了 `flate2`，所以 inflate 也是自研的；
  它与 Python `zipfile`/系统 `7z` 互相验证，见下。）

**实测**：`7z l -slt` 看自研打包结果 —— `opm.json` 方法 `Deflate`、`bg.png`/`song.ogg` 方法 `Store` ✓；
端到端（控制通道）新建→设音频/曲绘→存 `.opm`：容器 90 KB 音乐 + 361 B 曲绘 + 1 KB 谱面，
读回来 `meta.audio='song.ogg'`、`meta.background='bg.png'`（包内相对名）✓。
单测里 **7z 与内置实现互验**（7z 打的包内置读得回、内置打的包 7z 解得开）+ Python `zipfile` 造的
STORE/DEFLATE 包都能读 + CRC 校验 + 截断/坏 CRC 明确报错。

## 解压缓存、单会话，与「上次没有正常退出」

一次会话在磁盘上留下的东西只有一样：**解压缓存目录** `<临时目录>/opm/<内容 hash>/`。

```text
/tmp/opm/
├─ .session.lock        ← 单会话独占锁（文件很小；锁随句柄存在）
└─ 535767b4/            ← 一次会话摊出来的工作副本
   ├─ opm.json          ← 打开的谱面（编辑期会被**快照**刷新，见下）
   ├─ song.ogg          ← 资源（原样落盘，文件名 = 包内名）
   └─ session.json      ← 会话元数据：谁、什么时候、为哪个谱面摊的、有没有未保存的快照
```

**规则一：同一时刻只允许一个会话。** 启动时在缓存根目录上拿一把**独占锁**
（`File::try_lock`：Unix `flock` / Windows `LockFileEx`）。抢不到就**什么都不碰** ——
不开控制通道、不载入文档、退出也不清理任何东西 —— 只开一个**关不掉的模态**说明情况：

```
已经有一个 OpenPhM 在运行
同一时刻只允许一个 OpenPhM 会话：解压缓存是进程独占的，两个会话会互相删掉对方正在用的那份。
正在运行的那个：进程 167893（11 秒前 启动）
这一份没有碰任何缓存与谱面文件，直接关掉它是安全的。            [关闭]
```

为什么用文件锁而不是 pid 文件：锁**跟着句柄**走，进程被强杀时由内核释放 ——
"锁没人拿"与"进程已经不在了"是同一件事，不需要 pid 存活检测，也不会留下"假的活锁"。

**规则二：还躺在那里的 GUI 缓存目录 = 上一个进程没退干净。** 正常退出会删掉自己的目录，
所以启动时扫到一份 `exe` 是 `opm-app` 的目录，就说明上次多半是被强杀或崩溃了，于是问：

```
上次没有正常退出
上次运行时（22 秒前）有一份谱面还摊在缓存里：「容器测试」· 9.8 KiB · 22 秒前。
程序正常退出时会清理自己摊出来的缓存，这里还留着一份 ⇒ 上一个进程多半被强杀或崩溃了。
原始文件：/tmp/opmtest/pack.opm（还在）
缓存目录：/tmp/opm/535767b4
缓存里有未保存的改动（快照于 2 分钟前）—— 继续编辑会把它们带回来
[▶ 继续此谱面]  [🗑 丢弃缓存]  [稍后再说]
```

- **继续**：按缓存里的内容接着编辑，**保存目标指回原来那个文件**（不是 `/tmp`）；磁盘上那份如果更旧，
  界面直接显示「有未保存改动」。
- **丢弃**：删掉那份缓存；磁盘上的谱面文件一个字节都不动。
- **稍后再说**（Esc/点遮罩同效）：什么都不做，留着它，下次启动再问。
- **`opm-ctl` 留下的目录不会来打扰**：出处写在 `session.json` 里，只有 `opm-app` 的才算"没退干净"。
  反过来，`opm-ctl` 读一个包时**不碰**别人已经认领的缓存目录（`CacheClaim::ReadOnly`）——
  否则一次 `opm-ctl --file X dump` 就能把 GUI 崩溃留下的快照与元数据一起抹掉（这是实测到的）。

**编辑期快照（防"被强杀就全丢"）**：脏文档最多每 2 秒把 `opm.json` **原子替换**写回缓存目录
（先写 `opm.json.tmp` 再改名：强杀可能正好发生在写的中途，半截 JSON 比旧快照更糟），
并在 `session.json` 里记下"什么时候、当时脏不脏"。保存成功后这份快照随之变成"已保存"。
**与"退出时清理、未保存的数据按计划丢弃"不冲突**：那条说的是正常退出（守卫里选了不保存 ⇒
缓存随目录一起删掉），快照是**没走到退出**那条路上的兜底。

自动化钩子（截图/CI 用，与 `OPM_LAUNCH_AUTO` 同类，只在启动时读一次）：
`OPM_RESUME_AUTO=continue|discard|later`。

**载入的四种形态**（都是 `EditCore::stage_file` 认的，按内容判、不看扩展名）：

| 输入 | 判据 | 摊到临时目录？ |
|---|---|---|
| opm 容器 `.opm` | ZIP 里是 `opm.json` | 是 |
| RPE 谱面包 `.pez` | ZIP 里有 `info.yml` | 是 |
| opm 无压缩文件夹 | 目录里有 `opm.json` | 否（资源本来就是真实文件） |
| RPE 无压缩文件夹 | 目录里有 `info.yml` + `chart.json` | 否 |
| 裸 opm / RPE JSON | 既不是 ZIP 也不是目录 | 否 |
| 上一次留下的解压缓存 | 目录里多一份 `session.json` | 是（它本来就在临时目录里） |

**载入分两步**（`EditCore::stage_file` → `EditCore::load_staged`）：第一步只管"各种格式与打包情况
怎么摊开"，第二步是**唯一**把文档装进会话的入口。以前这两件事缠在一起各写一遍，
于是"启动那条路"漏了摊资源（用户报的"包里有音乐却装不上"），`.pez` 与无压缩文件夹更是
**只写得出去、读不回来**（`chart.json` 被判成 opm 谱面）。现在两者各只有一份实现。

## 启动检查：7z 能不能**调用**

`.opm` 容器靠 7-Zip 打包/解包，所以**启动时先检查 7z**（查的是"能不能真的跑起来"，不是"文件在不在"）：

- **探测顺序**：环境变量 `OPM_7Z`（显式指定，非标准安装/便携版的用途）→ `PATH` 里的
  `7z`/`7za`/`7zr` → **Windows 额外探常见安装目录**（`%ProgramFiles%\7-Zip\7z.exe`、
  `%ProgramFiles(x86)%`、`%ProgramW6432%`、`%LOCALAPPDATA%\Programs\7-Zip\7z.exe` ——
  7-Zip 的安装器不保证进 PATH，只查 PATH 会漏）。PATH 的分隔符按**目标平台**取（Windows 是 `;`）。
- **判定"可调用"**：起一次 `7z i`，能跑完且退出码为 0 才算可用 —— 装了一半、权限不对、架构不符
  都会在这里露出来。（Windows 上给子进程加 `CREATE_NO_WINDOW`，免得每次探测闪一个控制台窗口。）
- **没有 7z 时**：启动页上盖一层**关不掉的门槛模态**（`recents::missing_7z_modal`，用 `dialog` 的
  `sticky_modal`）—— 说明为什么需要它、给出具体的安装方法、**退出**按钮；
  **Windows 上多一个「获取 7z…」按钮**，按下用系统浏览器打开 7-zip.org 下载页。
  它不给 Esc/点遮罩关闭，但**仍然吃掉 Esc** —— 否则底下列表的"跳过"会当场把门槛漏掉（有单测）。
  带 `--doc` 直接进编辑页而系统缺 7z 时，编辑页上盖的是**同一个实现**。
- **命令行不受影响**：`opm-ctl` 没装 7z 时会用**内置实现**打包（全 STORE、不压缩、体积更大），
  保真度报告里会写明"打包后端：内置 zip 实现"。

## 谱面列表（起始界面）

打开程序先显示它：**左＝最近打开的谱面，右＝打开/新建**。记录存在
`$XDG_CONFIG_HOME/OpenPhM/recents.json`（这台机器的使用痕迹，**不进谱面文件、不进仓库**）。

- 条目显示曲名 + `[格式] 多久以前`；文件不在的条目变灰、点不动（并提示），可用 ✕ 从列表移除（**不删文件**）。

- `Esc` 或「跳过，直接进编辑器」用空谱面开始；`--doc FILE` 直接进编辑器（CLI/agent/截图都走那条）。

  内容按栏宽排布、而内容又决定容器尺寸 ⇒ 每帧在上一帧结果上再放大，
  表现就是"鼠标一滑，谱面列表横向一直变长"。这条有无头回归测试
  （`start_screen_drawn_width_is_stable_across_frames`：真实那段 UI 连跑 12 帧、量每帧画出来的宽度）。
- 打开或保存成功后自动记一条（去重、最近在前、最多 20 条；相对路径会绝对化，避免同一条目出现两次）。

## 显卡选择（Linux 混显笔记本）：默认核显，独显要显式指定

wgpu 的默认电源偏好是 `HighPerformance`，于是**什么都不设**时程序会去开独显。编谱是 2D、几十个实例的
活儿，核显足够，而独显（这台机器上是 RTX 5070 Max-Q）的功耗与发热高得多 —— 所以这里改成
**核显优先，独显只在显式指定时才用**：

| 怎么指定 | 结果 |
|---|---|
| 什么都不设 | **核显优先**（本机实测：AMD Radeon 610M / IntegratedGpu） |
| `prime-run opm-app …` | 独显（prime-run 设的 `__NV_PRIME_RENDER_OFFLOAD=1` / `__VK_LAYER_NV_optimus=NVIDIA_only` / `__GLX_VENDOR_LIBRARY_NAME=nvidia` 就是"我要独显"） |
| `DRI_PRIME=1` | 独显（Mesa 那套写法；`DRI_PRIME=0` 表示"不要"，不算指定） |
| `OPM_GPU=discrete` / `OPM_GPU=integrated` | 明确要独显 / 明确要核显（程序自己的开关，优先级最高） |
| `WGPU_POWER_PREF=high|low|none` | 尊重 wgpu 自己的偏好变量 |

## 平台契约：**只有 Linux 插手，Windows 保持默认选择器**

上面那一整套（ICD 白名单、后端集合、适配器选择器、`WGPU_POWER_PREF` 的翻译）**只在 Linux 生效**。
非 Linux 上"程序用哪块卡"完全交给系统那一套（Windows 图形设置 / 驱动面板 / 混合输出）：

| 会不会动 | Linux | Windows / macOS |
|---|---|---|
| 适配器选择器 | 装（默认核显优先） | **不装** |
| Vulkan ICD 白名单 | 默认摘掉 NVIDIA | **不碰**（连目录都不扫） |
| 后端集合 | 探到 Vulkan 就只开 Vulkan | **不碰**（egui-wgpu 默认 `PRIMARY \| GL`） |
| `WGPU_POWER_PREF` | 翻译成策略 | **不翻译** —— egui-wgpu 自己 `PowerPreference::from_env()` 读它，我们插手只会多装一个选择器 |

**唯一能越过这条线的是 `OPM_GPU`**：它明确写着"本程序自己的开关"，是用户点名要的，不是程序替他做的决定。
判定只有一处（`gpu::manages_gpu`），三处调用点都用它 —— 于是"Windows 不受影响"是结构性的，不靠谁记得加 `cfg`。

这条不是只写在文档里：`OPM_GPU_PLATFORM=windows|linux` 是**诊断钩子**，能在 Linux 构建上把整段当成
Windows 跑一遍（认不出的值退回编译期平台）。本机实测（`--trace-startup`，同一个二进制、同一台机器）：

| 跑法 | 启动日志 | 独显 `runtime_status` | 首帧 |
|---|---|---|---|
| Linux 默认（摘 NVIDIA ICD、只开 Vulkan、装选择器） | `保留 3 个：radeon/intel_hasvk/intel_icd.json` + `显卡选用: AMD Radeon 610M` | `suspended` **全程没被碰** | 248 ms |
| `OPM_GPU_PLATFORM=windows` | `非 Linux：不改 ICD、不改后端集合、不装适配器选择器` + `图形后端: 全部后端` + `显卡策略: 交给平台默认` | `suspended` → **`active`**（ICD 未被过滤 ⇒ 枚举到 NVIDIA） | **4773 ms** |
| `OPM_GPU_PLATFORM=windows OPM_GPU=integrated` | 上面三行 + `适配器候选 [1] NVIDIA GeForce RTX 5070` + `显卡选用: AMD Radeon 610M` | `active` | 5584 ms |

第二行是"Windows 分支真的没干预"的**硬证据**：枚举里出现了 NVIDIA 适配器、后端集合是默认的、日志里
根本没有 `显卡选用` 那一行（说明我们的选择器压根没装）。启动慢 4.5 s 也正是"枚举独显 + 初始化 GL"的代价。

启动日志会把 `显卡平台` / `图形 ICD` / `图形后端` / `显卡策略` / 每个`适配器候选` / `显卡选用` 打出来 ——
用了哪块卡、为什么、这一步是谁在做主，一眼可核对。

**在各种硬件组合上都验过**（本机能做的：直接换枚举集合来模拟；选择逻辑本身**完全不看厂商**，
只吃 `wgpu::DeviceType`，所以"AMD/Intel 独显"与"NVIDIA 独显"走的是同一条路）：

| 组合 | 怎么模拟 | 结果 |
|---|---|---|
| 核显 + 独显（本机真实） | —— | 选核显（AMD 610M） |
| **只有核显** | 只挂 `radeon_icd.json` | 选核显 ✓ |
| **只有独显** | 只挂 `nvidia_icd.json` | **照样选独显** ✓（不会因为"核显优先"就不给用硬件） |
| 只有虚拟卡 / 只有软件渲染 | `WGPU_BACKEND=gl LIBGL_ALWAYS_SOFTWARE=1` | 选 llvmpipe（`Gl/Cpu`）✓（比开不了窗口好） |
| 后端退化（Vulkan 里没有可用卡） | 只挂 `intel_icd.json`（本机无 Intel 卡） | 自动退到 GL 的 AMD 适配器并正常出图 ✓ |
| 完全没后端 | `WGPU_BACKEND=vulkan` + 假 ICD 路径 | eframe 报 `FailedToCreateSurfaceForAnyBackend` 后**可读退出**（不 panic）✓ |

另有 64 种适配器子集 × 2 种策略的穷举单测（不变量：有硬件绝不选软件、有核显必选核显、
只有独显必用它、结果确定），以及"策略不看厂商"的结构性测试；再加一条 **128 种环境组合的非 Linux 穷举**
（不看平台就断言"策略=交给平台、ICD 不干预、后端不动"，唯一的例外是 `OPM_GPU`）与平台钩子的单测。

## Windows exe（交叉编译）：能编、能在 Wine 上跑

```sh
rustup target add x86_64-pc-windows-gnu          # 一次性
cargo build --release --target x86_64-pc-windows-gnu --bins
# → target/x86_64-pc-windows-gnu/release/{opm-app.exe, opm-ctl.exe}
```

只需要 mingw-w64 链接器（Arch 上是 `mingw-w64-gcc`，给的是 `x86_64-w64-mingw32-gcc`）。
产物是 **PE32+ x86-64 控制台程序**，导入表里只有系统 DLL（`kernel32`/`user32`/`gdi32`/`dxgi`/`opengl32`/
`mmdevapi`/`ws2_32` + Universal CRT 的 api-set），**不含 `libgcc`/`libwinpthread`**（自包含）；
Vulkan 与 D3D12 是运行时动态加载的，所以**要求 Windows 10+**（api-set 与 DXGI 都在那之后）。

release 体积：**`opm-app.exe` 29.3 MB**（其中内嵌字 8.4 MB，见下）/ **`opm-ctl.exe` 8.5 MB**
（命令行那个**不留字体**：`include_bytes!` 的字节在那个二进制里没人引用，LTO 直接剔掉了 —— 实测 +0 KB）。

实测（本机 Wine 11.18 staging，**默认前缀 `~/.wine`**，不外建环境）：

| 检查 | 结果 |
|---|---|
| `opm-ctl.exe help` / `opm-app.exe --help` | 正常打印用法、退出 0 |
| `opm-app.exe --fonts` | 内嵌字体 + 355 字探针**全有字形**（见下节） |
| `opm-ctl.exe new --out rel2.opm --demo-notes 24` | 造出 9.9 KB 谱面；**本机 Linux 的 `opm-ctl` 能直接读**（格式互通） |
| `--file rel2.opm validate --json` / `overlaps` | 正常（校验按契约报 ERROR、退出码正确） |
| `--file rel2.opm render --at 1.5 --out rel2.png` | **wgpu 无头渲染成功**：480×270 PNG、24 个实例 → `artifacts/windows-exe-wine-render.png` |

—— 记一笔，不追（Wine 不是目标平台）。

### Wine 上那行 `create_factory_media failed: 0x80004002` 是什么

**无害，不用管**（查证全过程见《框架选型》§7.47）。一句话版：Wine 的 `dxgi.dll` 没实现
`IDXGIFactoryMedia`，而 wgpu-hal 建 DX12 实例时会**试探性**取一次这个接口，失败时先
`log::error!` 再被 `.ok()` 丢掉 —— 所以是"先喊一声，然后当作没有"，进程继续。
那个接口只用于"往合成表面里画"（`SurfaceTarget::SurfaceHandle`），**我们给的是 winit 的 HWND**，
走 `CreateSwapChainForHwnd`，压根用不到；真 Windows 8+ 上它存在，这行不会出现。

三条自证：`WGPU_BACKEND=vulkan` 跑一遍 → 这行**0 次**；`WGPU_BACKEND=dx12` → 可读退出
`dx12 found no adapters`（失败原因是没有适配器，不是这次探测）；Wine 自己的
`warn: DxgiFactory::QueryInterface: Unknown interface query 41e7d1f2-…` 里那个 GUID
就是 `IDXGIFactoryMedia` 的 IID。

**没去屏蔽它**：那个 log target 同时也承载真正的 DXGI 失败（`create_factory4`、`CreateSwapChainForHwnd`…），
按 target 关掉会把真故障一起吞掉。改成**只在 Wine 上**多打一行说明（判据：`C:\windows\system32\wineboot.exe`
存在，真 Windows 没有这个文件），于是"看着像故障"的那行旁边就有了解释：

```
  图形环境          : Wine（其 dxgi 未实现 IDXGIFactoryMedia）—— 若下面出现 `create_factory_media failed: 0x80004002`，那是 wgpu 的一次**可选**探测，已被丢弃、不影响渲染
```

## 字体：自带 CJK，不依赖系统字体

`egui` 默认字体**不含 CJK 字形**，不装载就是一片豆腐块。以前这里是 `fc-match`/`fc-scan` 去系统里找字体 ——
**Windows 上没有 fontconfig，那条路直接失效**（现场复现：Wine 默认前缀的 `C:\windows\Fonts` 是**空的**，
连拉丁字体都没有）。所以现在**把字体带在身上**：

- `app/assets/fonts/SourceHanSansCN-Regular.otf`（思源黑体 CN Regular，8.4 MB，**OFL-1.1**，许可原文
  `SourceHanSansCN-LICENSE.txt` 随字体一起在仓库里）用 `include_bytes!` 编进二进制；
- **单字面 SC 的 OTF**（索引 0 就是 SC）—— 顺便绕开 §7.1 那个坑：`NotoSansCJK-*.ttc` 里 0=JP/1=KR/2=SC，
  而 `FontData::from_owned` 固定用索引 0 ⇒ 加载集合会让中文用上**日文字形**；
- 于是**两个平台渲染完全一致**，而且启动少了 `fc-match` + `fc-scan` 两个子进程与 8 MB 读盘；
- 想换字体：`OPM_FONT=<字体文件>[:字面索引]`（指了却读不到 ⇒ **回退内嵌**，不会因为一个坏路径变豆腐块）；
- 韩文：内嵌那份不含 Hangul，Linux 上照旧借系统 `NotoSansCJK-Regular.ttc` 的 KR 字面（`install_kr_fallback`）。

**"不会出豆腐块"是可执行的**：`opm-app --fonts` 造一个无头 egui、装上字体、拿 **355 字的探针**
（界面词汇 + 常见汉字/标点 + 拉丁数字 + 假名）逐字问 `has_glyphs`，缺任何一个就退出码 3：

```console

字体许可          : 思源黑体 CN Regular © Adobe，SIL Open Font License 1.1（原文见 app/assets/fonts/SourceHanSansCN-LICENSE.txt）
$ wine opm-app.exe --fonts        # Windows 二进制、默认 wine 前缀（那边一个字体文件都没有）
（同上两行）
```

同一条断言也在单测里（`fonts::tests::embedded_font_covers_the_probe_text`）—— 无头、无需 GPU，
所以 Linux 与 Windows 上是同一条。

## 快速放置音符：Q/W/E/R（hold 跟随鼠标）

在编辑区里把指针放到音符区，按一个键就放下一个音符 —— 不用先点工具栏选类型：

| 键 | 放下什么 | 说明 |
|---|---|---|
| `Q` | tap | 落在**指针处**，位置按两轴网格吸附（与拖拽/双击同一套吸附） |
| `W` | flick | 同上 |
| `E` | drag | 同上 |
| `R` | hold | **第一次按 R 进入"跟随"状态**：起点定在指针处，长度随鼠标移动 |

**事件区只认 `R`**：指针放在事件区（右半边）的某一列上，按 `R` 就在**那一列对应的轨道**上起一个
事件块草稿 —— 跟 hold 完全同一套流程（长度随鼠标、控制杆、`Esc` 取消、`R`/回车/左键放下）。
`Q/W/E` 在事件区**没有任何反应**（它们只对音符有意义；早先在这里也会起事件草稿，那是误触，用户报的）。
规则是纯函数 `overlay::quick_key_rule`，有单测钉四个键 × 三个半区的全部组合。
新事件的值取**该轨道此刻的值**（放一条平段 ⇒ 画面不跳变）；轨道为空时才用中性值
（移动/旋转 0、透明度 1、流速 10 = RPE 的默认流速）。

**确认方式（hold 与事件块草稿一致）**：`R`、`Enter` 或**鼠标左键点一下**都能放下；`Esc` 取消。
草稿期间左键不再用于点选（那时候它属于"放下"）。

**hold 跟随状态**（唯一有中间态的）：

- 鼠标移动 ⇒ 终点跟着走（长度有下限：一个网格步长，反向拖不会把长条拖没）；
- **`R` / 回车 / 左键 = 放下**；**`Esc` = 取消**（草稿不进撤销栈，取消等于什么都没发生）；
- 也可以拖它的**时间控制杆**：与事件块**同一套**头/尾把手（`overlay::TimeHandle`，
  命中判定与画出来的样子同源：头 = 实线 + 短竖标记、尾 = 实线）；
- **滚动与缩放照常**：跟随期间滚轮仍然移动时间轴、Ctrl+滚轮仍然缩放（跟随只认"指针移动"，
  所以滚动不改长度）—— 这条有单测钉住；
- 按键**忽略自动重复**：按住 `R` 不会"放一个又开始放一个"。

指针不在音符区也不在事件区（标尺/轴带上）时按键会在状态栏说明原因（不静默失败）；
在事件区按 `Q/W/E` 则是**完全静默**的（那里没有它们的语义，但也不该报错）。

自动化钩子：`OPM_EDIT_AUTO=hold:<lane>,<start>,<end>` 或 `OPM_EDIT_AUTO=event:<track>,<start>,<end>`
启动就把"正在跟随的草稿"摆出来（截图/自检用；没人能往窗口里注入按键，这是唯一能把它拍下来的办法）。
工件：`artifacts/pending-hold.png`、`artifacts/pending-hold-handles.png`、`artifacts/pending-event.png`。

## 按键也能被"真的按一遍"：`OPM_KEY_AUTO`

```sh
OPM_KEY_AUTO=30:Delete                 opm-app --doc x.opm --shot /tmp/a.png --shot-frame 80 --shot-exit
OPM_KEY_AUTO=30:Delete';'70:ctrl+z     opm-app --doc x.opm --shot /tmp/b.png --shot-frame 100 --shot-exit
```

语法 `[帧号:]按键[,按键]`，多组用 `;` 分隔（帧号用来等前面的视图命令到位 —— 第 1 帧选区还是空的，
那时按 Del 只会说一句"没有选中的东西"）。键名是 `egui::Key` 的名字，前缀支持 `ctrl+`/`shift+`/`alt+`。

为什么需要它：**Wayland 下没人能往窗口里注入按键**（xdotool 要 `DISPLAY`），而"按键 → 动作"这一段
（Del 删选区、`Ctrl+Z` 撤销）恰恰是最容易接线接错的地方。注入的是一次性 `Event::Key`，
走的路径与用户按下去**完全相同**，门槛也一样（在文本框里打字、模态开着时都不吃）。

**踩过的坑（写在实现旁边）**：修饰键不能靠往 `InputState.events` 里塞 `Event::ModifiersChanged`
—— `InputState::begin_pass` 是从 **RawInput** 的事件里算出 `modifiers` 的，那一遍循环早就过去了；
塞事件只让 `key_pressed` 为真，`modifiers.command` 仍是 false，于是 `ctrl+z` **一声不响地什么都没做**
（实测：日志里根本没有 `[core] update`）。正确做法是直接写 `i.modifiers` —— 与真实事件的效果完全一致。

实测（2026-09-28，`--verbose-updates` 的 [core] 留痕，工件 `artifacts/multi-select-{deleted,undone}.png`）：

```text
  OPM_KEY_AUTO     : 帧 30 注入 1 次按键（Delete）
[core] update #2 Local del_note[0:2] → [Note[0], Notes[0]] → 投递 1/1 订阅者
[core] update #3 Local del_note[0:1] → [Note[0], Notes[0]] → 投递 1/1 订阅者
[core] update #4 Local del_note[0:0] → [Note[0], Notes[0]] → 投递 1/1 订阅者
  OPM_KEY_AUTO     : 帧 70 注入 1 次按键（ctrl+z）
[core] update #5 Local undo: 删除选中(3 条) → [Note[0], Notes[0]] → 投递 1/1 订阅者
```

三条 `del_note` 的索引是 **2、1、0**（同表降序，顺序错了会删错东西），而 `Ctrl+Z` **一步**把三条都带回来
（标签 `删除选中(3 条)` = 一次事务）—— 这一整条就是"Del 的语义"的可执行证据。

多选本身也能从控制通道指过去（截图复核用，选区是视图状态所以走视图通道）：

```sh
opm-ctl --attach auto --cmd '{"op":"select","notes":[0,1,2]}'
opm-ctl --attach auto --cmd '{"op":"select","events":[["alpha",0],["alpha",1]]}'
```

工件：`artifacts/multi-select-notes.png`（已选 3 个音符 + 三处白框 + 标题下一行读数）、
`artifacts/multi-select-events.png`（已选 2 条事件）、`multi-select-deleted.png`（删完：音符 8→5、底栏"已删除 3 个音符"）、
`multi-select-undone.png`（`Ctrl+Z` 之后音符回到 8）。


## 空格键：单点切播、长按试听

| 操作 | 行为 |
|---|---|
| **单点空格**（< 0.28 s） | 停着 → **进入**自动播放；播放中 → **退出** |
| **长按空格**（≥ 0.28 s） | 按住期间播放，**松手退出**（像"按住试听"） |
| 播放中按下 | **立刻**暂停（不等松手 —— 单点退出要即时反馈） |

规则是一个纯状态机 `keymap::SpacePlayback`（库内，7 条单测覆盖四种组合与边界），主循环只负责
把「按下 / 松开 / 当前时刻 / 当前播放状态」喂进去：
**同一件事不再有第二份实现**（旧的"按下就 toggle"已删除，`tests/audio.rs` 里那份手抄的规则副本也换成了调真身）。

两个刻意的设计：
- **长按松手只停"本次按下才开始播"的播放** —— 否则松手会把用户自己之前的播放状态一并停掉；
- 打字（控制台有焦点）或模态框（文件/新建/未保存守卫）期间按下会**复位**状态，
  否则松开时会拿一个陈旧的按下时刻去算"长按"，冒出一个莫名其妙的暂停。

阈值常量只有一处：`keymap::SPACE_HOLD_SECS = 0.28`（**故意不加旋钮**：多一个旋钮就多一种说不清的手感）。

## 音频播放与自动播放

**播放头跟着音频时钟走，不跟墙钟**。谱面与音乐各走各的时钟会一直累积误差（S2 spike 实测两者相对漂移
7.4 ppm ≈ 每小时 27 ms；看着谱面打拍子要的是"**此刻听到的那一帧**在哪"）。所以：

```text
cpal 输出回调（实时线程）──写──▶ Arc<AtomicU64> 已送入设备的**帧数**（唯一真相）
                                      │
GUI 线程 ──读──▶ 播放头 = 帧数/采样率 − 输出延迟 + 用户校准
```

输出延迟由 cpal 的 `OutputCallbackInfo::timestamp()` **自校准**（`playback.duration_since(callback)`
就是"这批样本多久之后才会响"），不写死经验值；换设备/换 buffer 都不用改代码。剩余偏差用校准旋钮补。

```sh
opm-app --doc x.opm.json                                   # 音频取谱面 meta.audio（相对谱面目录）
opm-app --doc x.opm.json --audio song.wav                  # 显式指定
opm-app --doc x.opm.json --audio off                       # 明确不要音频（播放头退回墙钟）
opm-app --doc x.opm.json --audio song.wav --autoplay        # 启动即播
opm-app --doc x.opm.json --audio song.wav --audio-offset-ms -12   # 手动校准
```

### 自动播放：音符到线、闪一下、消失（hold 每 3 拍再闪一次）

演奏区是"游戏里会变成什么样"的唯一视图，所以自动播放时的**击打**也要像游戏：

- **音符到达判定线就停在线上**（不再从线下面继续往下掉），用 `HIT_FADE_SEC = 0.06 s` 收缩淡出，
  之后彻底不画了；
- 到线那一刻出现**击中效果**：一个白闪 + 一圈向外扩散的方框（渲染层只有实例化的方块可用，
  所以"环"是四条细边拼的空心方框，跟着判定线一起旋转）。效果持续 `HIT_FX_SEC = 0.22 s`；
- **hold 击中后立即播一次**，之后**按住期间每 `HOLD_PULSE_BEATS = 3` 拍再播一次**（直到它的尾巴）；
- **被按住的那一段不再画**：hold 的身子从**判定线**起算，而不是从头起算 —— 看起来就是"被吃掉"；
- **假音符没有击中效果**（它没有判定，游戏里也不闪），但同样会到线消失。

渲染是每帧重算的（没有"事件"这个对象），所以"播一次"落实成"在某个时刻之后的一小段窗口里画它"
（`render::hit_fx_progress`：算出此刻该不该有一个效果在场、它的进度是多少）。
两个时长与脉冲间隔都是**常量**，拍→秒的换算走 `TimeMap`，所以 BPM 变化时"每 3 拍"仍然准确。

**顺手修掉的两个真 bug**（都是被这次改动暴露出来的）：

1. **消失进度没夹到 0**：`age = 播放头 − 打击时刻`，还没到的音符 `age < 0` ⇒ 进度为负
   ⇒ 音符被放大到 2.8 倍、alpha 乘到 5.5（实测：一个 510×144 的亮蓝块挂在窗口顶上）。
   现在夹到 `[0, 1]`，并有单测钉住"还没到线的音符是原尺寸 + alpha 1"。
2. **长 hold 的头被击中、身子还在窗口里时整条不再上报实例**：`visible_range_of` 过去只按
   **时间**回退 0.15 s，而音符是按时间排序的 —— 一条 40 拍的长条在头过去之后就被排到区间之外了。
   现在下界按**这条线最长音符的时长**回退（`Line::max_note_sec`，是个正确的下界），
   渲染侧再逐条判"与窗口相交"。同理，裁剪判据取**最低的那一端**（否则尾巴远在窗口之上的长条
   会被整条裁掉）。

证据（截图都是 `--overlay off` + 控制通道 `seek` 到精确时刻拍的，这样停在那一帧上不会被编辑区挡住）：
`artifacts/hit-effect.png`（一个 tap 的击中效果正压在判定线上）、
`artifacts/hold-pulse.png`（按住中：身子从判定线往上 + 3 拍的那次脉冲）、
`artifacts/note-vanishes-at-line.png`（音符停在线上收缩 + 效果框）。
自检：`cargo test --test lines` 的 `a_note_hits_the_judge_line_then_vanishes`、
`a_hold_pulses_a_hit_effect_every_three_beats`、`a_held_hold_body_starts_at_the_judge_line`、
`a_long_hold_stays_visible_after_its_head_is_hit`、`a_fake_note_does_not_flash`。


播放控制有**两个入口，同一条代码路径**（`App::toggle_play`）：

| 入口 | 用法 |
|---|---|
| 键盘 | **空格** 播放/暂停（控制台输入框有焦点时空格是打字，不触发 —— 这条规则有单测钉着） |
| GUI | 工具栏 `▶ 播放 (空格)` / `⏮ 回到开头` |
| CLI（附着到运行中的 GUI） | `{"op":"grid","beatDiv":4,"laneDiv":16}`（改网格）、`{"op":"zoom","beats":8}` / `{"op":"zoom","factor":2.0}`（改缩放）、`{"op":"window","offsetX":400}`（窗口 X 偏移）、`{"op":"play"}` `{"op":"pause"}` `{"op":"toggle_play"}` `{"op":"seek","to":12.5}` `{"op":"seek","beat":48}` `{"op":"audio","path":"new.wav"}` `{"op":"audio_offset","ms":-12}` |

⚠️ 视图命令的响应只承诺"**已受理**"：播放头/播放状态是**视图状态**（不属于文档、不进撤销栈），
在下一帧生效。要确认效果就读 `ui_stats`（或 `{"op":"view"}`）里的 `playing` / `playhead_sec` / `playhead_beat` / `audio_pos_ms`。

### 实测（180 BPM 节拍器 WAV，48 kHz，本次机器：PulseAudio → USB 声卡）

| 项 | 实测 |
|---|---|
| 播放头 vs 音频游标 | **同一位置**（差值 = 一帧内的推进，统计快照里 0.00 ms） |
| 输出延迟（自校准） | **24.00 ms** |
| 速率 | 稳定期后按斜率测：−84 ~ +715 ppm（几次窗口），偏差在 ±7 ms 内**有界振荡、不增长** |
| 回调欠载 | 0（20 秒连续播放） |
| `{"op":"seek","beat":48}`（180 BPM） | 播放头 = **16.0000 s**（48×60/180） |
| 暂停 1.2 s | 播放头一动不动（0.00 ms） |
| 播到音频末尾 | 干净停下（`playing=false`），无欠载 |
| 服务器侧 | `pactl`: `float32le 2ch 48000Hz`、`Corked: no` —— 确实在推数据 |

**偏差口径**：只报 ppm 会骗人 —— 短窗口下一帧的采样抖动（4~16 ms）就能算出几千 ppm 的假数字。
所以先跳过 1 秒稳定期、再按**斜率**算速率，并同时给出**累计偏差（ms）+ 窗口（s）**：偏差有界即通过。

### 格式：主流格式都能读

解码交给 **symphonia**（纯 Rust、活跃维护）。实测五种格式都从同一份 48 kHz 单声道素材解出 60.000 s：

| 文件 | 解码器 | 结果 |
|---|---|---|
| `click180.wav` | PCM (wav) | 48000 Hz / 1ch / 60.000 s |
| `click180.flac` | FLAC | 48000 Hz / 1ch / 60.000 s |
| `click180.mp3` | MP3 | 48000 Hz / 1ch / 60.000 s |
| `click180.ogg` | OGG Vorbis | 48000 Hz / 1ch / 60.000 s |
| `click180.m4a` | AAC (m4a) | 48000 Hz / 1ch / 60.032 s（编码器补帧，正常） |

内建覆盖还包括 ALAC、ADPCM；**识别不出容器或没有音频轨时给明确原因**，不静默无声。查一个文件能不能用：

```sh
opm-app --audio-probe song.ogg     # 只解码、不开窗口，打印 JSON（给 agent 用）
# {"codec":"OGG Vorbis","sampleRate":48000,"channels":1,"frames":2880000,"durationSec":60.0}
```

> 早先手写过一个"只读 WAV"的解码器（唯一优势是零依赖）。一旦需求变成"主流格式"，自己写 OGG/MP3 解码器
> 就不是省事而是冒险 —— 换成 symphonia，把自研留在**该自研的地方**（判定线/事件/格式）。

其余边界：声道/采样率不匹配时做**线性重采样**（预览够用，不做隐藏的音质承诺）；输出流只走 **f32**，
设备默认格式不是 f32 时直接报错（不悄悄降级）；播放头被**谱面时长**截断，音频更长时走到音频末尾才停。

## 下落速度（流速）：与 RPE 一致

**1 单位流速 = 120 RPE y 单位 / 秒；判定线的默认流速 = 10**（= 1× = 1200 单位/秒）。
于是流速 10 的音符 **0.75 秒竖直划过整个 900 高的窗口**（`(450+450)/1200`）。

出处（RPE 官方手册《Re:PhiEdit 使用手册》的谱面内说明，2026-09-28 取证）：

> 速度：浮点数 v，音符的实际速度由 v×判定线该时刻基准速度决定，实际速度为 10.0 表示音符每秒钟移动
> 10.0×120 = 1200 像素，这意味着其会在 (450+450)/1200 = 0.75 秒内竖直划过整个屏。

三条独立佐证：RPE 编辑器新建谱面的**判定线列表**那行印着 `10.00V`（基准速度 = 10）、音符编辑器印着
`1.00`（音符自身的 speed 默认 1.0）；第三方 RPE 复刻编辑器 PhiEdit-2573 的 `SPEED_RATIO = 120`
且新建谱面写 `speedEvents[0] = 10`；真实 RPE 谱（Belle de Nuit / glacia）里流速事件的取值众数是 10.0。
**prpr（Phira 的格式库）取 120.23** —— 差异 0.19%，来源是它把屏幕高比写成 `0.83175` 而不是 `1/1.2`；
我们按手册取整 120（`perf::SPEED_UNITS_PER_SEC`）。

音符的纵向位置按 **floor position** 算（不是"时间差 × 一个常数"）：

```text
y_local = (H(t_音符) − H(t_此刻)) × 音符自身 speed        H(t) = 120 × ∫ v dτ   （τ 在秒域）
```

- **是积分，不是瞬时值**：缓动段里 v 一直在变，所以按段积分（事件边界当必须的抽点，段内 8 点梯形法）。
  线性段因此是精确的（梯形法对线性就是精确积分），其它缓动是高精度近似 —— prpr 对带缓动的事件同样是数值积分。
  实现见 `perf::speed_travel` / `perf::SpeedAccum`（**只有一份**积分实现，直接查询与单调累加共用）。
- **与 BPM 无关**：流速是"每秒"不是"每拍"。同一条流速事件在 120 BPM 与 240 BPM 下每秒走的距离一样，
  每拍走的距离减半。BPM 只通过"拍↔秒"换算进来。
- **音符自身 `speed`（文档字段，默认 1.0）乘在"离判定线的距离"上**：它不改到达时刻，只改这一路落多远
  —— 取 3 就三倍远（于是可能 0.25 秒就跑出窗口）。Hold 的头与尾同乘（prpr 与 PhiEdit-2573 都是这么做的）。
- **没有流速事件时按默认 10 走**（`perf::SPEED_DEFAULT`）。prpr 对"一条流速事件都没有"的线给 0（音符冻住），
  那是播放器的选择；编辑器里冻住的预览等于什么都看不见，所以这里按 RPE 的默认值兜底。
- **编辑器与 RPE 的差异只有一处**（如实说）：RPE 1.7.0 前后"流速缓动"的语义变过一次
  （`behaviorProfile` 里的 `rpe-pre-1.7` / `rpe-1.7`）。我们实现的是 **1.7 之后那套**（缓动值就是"此刻的流速"，
  再积分），因为本编辑器的求值器本来就是这个口径；文档里的老档位仍原样透传、不影响预览。

实测（`tests/lines.rs::notes_fall_at_the_rpe_speed`）：BPM 120、流速恒 10 时，
0.1 秒后打击的音符落在 **120** 单位处、0.3 秒后落在 **360**（= dt × 1200），同一条线上 0.5 秒后的音符
（600 单位）**不再上报实例**（已飞出 ±450 的窗口）；把流速改成 20 则 0.1 秒后是 240、0.3 秒后的飞出窗口。
另一条测试把手册那条算例直接钉死：流速 10 走 0.75 秒**正好** 900 单位。

性能（本机 RX 610M 核显，1600×900，`--bench`）：400 音符 p50 实例构建 **0.006 ms**、
4000 音符 **0.009 ms** —— 成本只与"窗口内的流速事件条数"有关，与音符数量无关
（单调累加器：音符按时间升序，一次走完）。

## 预览区的窗口边界与判定线长度

**RPE 口径**（[Phira Documents · 普通事件](https://teamflos.github.io/phira-docs/chart-standard/chart-format/rpe/event.html)）：
坐标系锚点在屏幕中心，**X ∈ [−675, 675]，Y ∈ [−450, 450]**，即窗口是 1350×900 的 3:2 矩形。
预览区是等比 letterbox 的，所以"窗口边界不一定顶到预览区边缘"—— 必须画出来，否则哪块是游戏画面只能靠猜。

预览里现在有三样东西：

| 元素 | 含义 | 来源 |
|---|---|---|
| 边框 + 8 个角标 | RPE 窗口边界（±675 × ±450） | 渲染层按 RPE 坐标画（与内容同一套映射） |
| 边框外压暗 | 边界外不是游戏画面；**压暗画在内容之上**，所以"跑到窗口外的音符"会变暗但仍看得见（这是个该被发现的错误，不该被藏起来） | 同上，4 个实例块 |
| 判定线端点（黄色圈 + 刻度）与"线 #N 长 L" | 判定线长度与它的两端在哪 | 线段本身由渲染层按线长画 |

**判定线长度是编辑器设置，不是格式字段**：RPE 的判定线对象只有 name/bpmFactor/zOrder/isCover/layers/notes，
线画多长属于呈现约定，所以 opm 也把它留在编辑器里。**默认长度 3000**（`state::RPE_LINE_LEN_DEFAULT`，
比窗口的 1350 宽得多）—— 判定线常常被旋转/缩放，长一点更容易看清"它此刻在哪、朝哪边"。
线长超过窗口时两端会被画面裁掉，这时的处理是：端点圆圈只画**看得见的**那些，
而"线 #N 长 L（伸出窗口）"这行读数贴在**窗口内**的那一端（右对齐），保证它永远看得见。

```sh
opm-app --line-len 1350            # 与窗口同宽（老默认）；任何值都行
opm-app --boundary off             # 只关边框，不改判定线长度
opm-ctl --file x.opm.json render --line-len 1600 --no-boundary --out a.png
```

证据：`artifacts/judge-line-3000.png`（默认线长下"线 #0 长 3000（伸出窗口）"贴在窗口右边缘）。

### 音符"会不会被裁掉"：构建窗口按**流速**算，不是固定 2 秒

音符进入窗口的时刻由流速决定：从窗口边缘（±450 + 一个音符的余量）走到判定线要
`510 / (120·|v|)` 秒 —— 流速 10（默认）是 0.42 秒，流速 1 是 **4.25 秒**。
所以实例构建窗口过去那个**固定 2 秒前瞻**在慢流速下会漏画：实测（流速 1、播放头在 0）
3 秒处那颗音符的偏移是 360（**就在窗口里**），却整颗没有实例 —— 它会"凭空出现"。

现在窗口由 `Line::min_speed_abs`（这条线流速的**最小非零量级**，逐事件采样 16 点）算出来，
`lookahead` 退化成它的**下限**（保证那个设置仍然有意义），上限 30 秒（流速趋近 0 时别把整份谱面
都塞进实例列表）。

**判据是"屏幕上的位置"，不是"离判定线多远"** —— 这一条也是踩出来的真 bug：
构建窗口里那一步曾经只看**线本地**的偏移（`|offset| > 510 就跳过`），而判定线是会被事件
移开/旋转的：

- `moveY = -300`（线被移到下面）时，偏移 660 的音符在屏幕上的 y 是 **+360** —— 明明在窗口里，
  却被当成"离判定线太远"整颗丢掉；
- 线旋转 90° 时，同样的音符落在屏幕 x = **-660**（±675 之内），同样被丢掉。

现在判据改成：把这颗音符（连它的半宽半高、按旋转取外接半径）变换到屏幕坐标，
看它的**包围盒是否与窗口相交**；余量仍是 `EditorState::NOTE_SPAN_MARGIN = 60`。
断言在 `notes_inside_the_window_are_drawn_however_far_they_are_from_the_line`（三种线位姿逐一对账）。
证据：`artifacts/note-visible-with-offset-line.png`（线在 y=−300，音符一直画到窗口上沿）。

**"所有音符都能显示"是可执行的断言**（`tests/lines.rs::every_note_becomes_visible_inside_the_window_before_its_hit`）：
流速取 10 / 3 / 1 / 0.5，五颗音符横向铺在 ±600 上，逐帧扫过"进画面"的整个过程，断言
①每颗都在窗口里**完整地**出现过（中心离边缘还有 30 单位），
②从没有哪一帧被建到余量之外，③横向 `|中心| + 半宽 ≤ 675`（**不被横向裁掉**）。

> 关于横向：官方窗口就是 ±675，`|laneX| + 音符半宽 > 675` 的音符（越界坐标，`validate` 只给警告）
> 在游戏画面里本来就在外面。编辑这类音符用顶栏的 `窗口 X 偏移`（见上文），预览永远显示真实窗口。

### 负流速（音符从判定线下面飞上来）

RPE 规范：**流速为负时音符向上飞**。流速积分、命中时刻、击中效果本来就与符号无关，
"画在哪"则统一到上面那条规则上：**只要在可见区域就画**（不管它在线上面还是线下面）：

- 负流速下音符出现在**判定线的下方**并向上飞，越接近打击时刻越靠近判定线
  （`a_negative_flow_speed_brings_notes_up_from_below` 逐点对账：0.3 秒前 −360、0.1 秒前 −120）；
- 到线那一刻播**击中效果**，之后本体停在线上收缩消失；
- 音符自身的 `speed` 字段也**带符号**（负值把方向翻过来，与负流速是同一套几何），
  属性编辑器里它的范围放成 `-20..=20`；`speed = 0` 的东西一律不渲染（RPE：速度 0 ⇒ 长度 0 ⇒ 不渲染）。

> 上一轮把"音符在判定线之下时不用显示"读成了"到线之前一律不画"，于是负流速段什么都看不见。
> 按后来的要求（"音符只要在可见区域就要显示"）统一成一条**屏幕空间**的判据：
> 在线下面但在窗口里 ⇒ 照画。

证据：`artifacts/negative-speed-hit-flash.png`（到线那一刻闪光）、
`slow-speed-note-enters.png`（流速 1、播放头 0：3.5 秒处那颗音符正确地贴在窗口上沿，
修构建窗口之前它是**不显示**的）。

GUI 里对应工具栏的 `边界框` 勾选框与 `线半长` 拖动框；无头出图默认也画边界（给 agent 的图需要同一套参照）。

⚠️ 压暗的 alpha 与色彩空间：若渲染目标是 **sRGB**，硬件在线性空间混合，同样的名义 alpha 观感会弱得多
（实测名义 0.42 只得到 0.78 的观感变暗，`56 → 42`）。因此 `render::dim_alpha_for()` 按目标格式换算，
让 GUI（`Rgba8Unorm`）与无头出图（`Rgba8UnormSrgb`）尽量一致 —— 这是**近似**：sRGB 不是纯幂函数，
不存在对所有亮度都精确相等的 alpha（暗背景约 0.48、中灰约 0.53，目标 0.58）。

## 关键设计

- **演奏区用 viewport 映射，不靠裁剪**：`PlayfieldFrame::paint()` 用 `info.viewport_in_pixels()` 把 viewport 设成回调矩形，着色器按
  `scale_px = min(vp_w/1350, vp_h/900)`（等比 letterbox）把 RPE 坐标（x∈±675, y∈±450）映射到该矩形，画完恢复全屏 viewport。
  ⇒ 面板布局变化、分数 DPI 缩放都不会错位。**不要**用"铺满全屏 NDC 再被裁剪"的写法（S1b 踩过：矩形超出裁剪区会让 egui 静默丢弃整个回调）。
- **CJK 字体必须自己装**（`src/fonts.rs`）：egui 默认字体无 CJK 字形；且 `NotoSansCJK-Regular.ttc` 的字面索引是 **0=JP、1=KR、2=SC**，
  而 `FontData::from_owned` 固定用索引 0 ⇒ 直接加载会让中文用上日文字形且不报错。本实现**内嵌单字面 SC 的 OTF**（索引 0 就是 SC，从根上避开这个坑）；
  唯一还在用 `fc-scan` 的地方是 Linux 的韩文回退（借系统 TTC 的 KR 字面）。
- **时间轴自适应抽稀**：整谱可见时拍线密度会远超像素密度（20 万音符的谱面曾画出 5 万条线，把帧时间拖到 20 ms）。
- **对齐自检**（`--verify-align`）：RPE 四角与中心同时由自研管线（品红方块）与 egui 画笔（青色十字）绘制，两者重合即映射正确。

## 更新广播：EditCore 是唯一可写方，GUI 只是订阅者

**数据流是单向的，没有反向边**：

```text
GUI 控制台 / 远端 opm-ctl
   └─▶ EditCore::exec            唯一可写方；改完**立刻**发一条 update 广播
         └─▶ 广播（带细粒度话题 + origin + revision）
               └─▶ 订阅时带过滤器的订阅者才收到（话题不命中 = 一条都不发）
                     └─▶ GUI 把话题映射成面板脏位 → 只重建脏掉的那块
```

三条硬约束（都有可执行证据）：

1. **GUI 不私自更新**：`src/main.rs` 里对文档的**写**路径只有一条 —— `App::dispatch()` 调 `EditCore::exec_batch`。
   面板读到的全是缓存（`meta_name` / `list` / `sel_view` / `state.chart`），只在收到广播后重建；
   命令发出去后界面**故意停在旧状态**，状态栏会亮 `⏳ 等广播`，直到广播到达才更新。
2. **无关控件不参与更新**：订阅带过滤器（`TopicFilter`），且 GUI 内部按话题置脏位。
3. **失败的命令不广播**：文档没变就不该叫醒任何人。事务内的改动**逐条广播**（拖拽要实时看到），
   而撤销仍按事务**一步**计 —— 广播粒度与撤销粒度是两件事，早先绑在一起导致拖拽过程中界面不更新。
   `abort` 会**回滚文档**并再发一条全量话题让订阅者重取。

**界面这一侧的写路径也只有一处**：所有"手势 → 命令"的拼装在 `opm_app::edit`（纯函数，有单测）——
拖音符（hold 要保持时长）、拖事件头尾、双击放音符、检查器/树上的字段编辑、切分事件（**毫拍有理数**，
不是浮点拍）都在那里。UI 只负责"画"和"把动作交给命令路径"，不自己拼 JSON。

**这套边界现在由编译器兜底，不再只靠约定**：

- `EditCore::doc` 私有，唯一的读入口是 `doc(&self) -> &Document`（**没有** `&mut` 版本、
  没有 `RefCell`/`Mutex<Document>`/`unsafe`/`Deref` 之类的后门）；
- `path` / `revision` / `source_format` / `assets` / `journal` / `subscribers` 等状态字段一律私有，
  外部只能通过窄接口读，要改就得走 `exec`；需要外部设置的只有两处（GUI 开 **verbose**、
  控制通道给远端命令打 **origin** 标记），走各自的 `set_*` 方法 —— 方法名自己说明"这是给谁用的"；
- `journal` 里那几个"拿 `&mut Document` 直接改文档"的写原语降为 `pub(crate)`：
  GUI/CLI 是**另一个 crate**，从此**编译不过**（而不是"靠自觉不去调"）。

**保存链路上那条唯一的例外也补上了**：写 `.opm` 容器时要把 `meta.audio`/`meta.background`
规范成包内相对名。它原先**直接在保存过程里改内存文档**（没 `+revision`、没广播 ⇒ 界面缓存看不见它），
而且改名发生在 `write_file` **之前** ⇒ 写盘失败就会留下"文档被改、文件没写、没有任何信号"的状态。
现在：改名先算在**副本**上写出文件，文件真的写出来了，才**走 `{"op":"set_meta"}` 命令**落到内存文档
（记 journal、可撤销、按话题广播）—— 保存要么完整发生，要么什么都没发生。

第四条（补上的一条）：**空话题的广播 = "什么都可能变了"，必须送到每个人手里**。
`Subscribers::emit` 是"话题命中才投递"，而"一条记录不出任何改动的命令"正好会给出空话题 ——
那条广播原先发给 **0 个订阅者**：revision 涨了、界面却不知道（静默丢更新）。
现在 `emit` 自己把空话题补齐成全量话题（有单测钉住两个方向：空话题必须到、普通话题仍要过过滤器）。

### 话题 → 脏位（唯一映射表，`opm_app::dirty::dirty_of_topics`）——**粒度到"哪条线的哪一部分"**

| 话题 | 整表重建 | 该线属性 | 该线**子音符** | 该线**事件轨道** | 工具栏 | 检查器 | 演奏区 |
|---|---|---|---|---|---|---|---|
| `Meta` | — | — | — | — | ✅ | — | — |
| `Bpm` / `LineList` | ✅ | — | ✅（全部线） | ✅（全部线） | ✅ | ✅ | ✅ |
| `LineProps[i]` | — | ✅ | — | — | — | — | ✅ |
| `Notes[i]` / `Note[i]` | — | — | ✅ | — | ✅ | ✅ | ✅ |
| `Track[i]`（移动/透明度/流速） | — | — | — | ✅ | — | — | ✅ |

关键点：**改一条线的一部分，不动其他线、也不动其他面板**。改 `Track[3]` 只重建 3 号线的轨道缓存；
3 号线的子音符缓存、4 条线的整表、音符列表、检查器全部跳过（计数可验证）。
`LineProps` 会牵连 `bpmFactor`，因此事件话题**不得**附带 `LineProps`（见 §已知问题里的实测教训）。

### 观测：把"谁被更新了"暴露给外部

```sh
# 收到几条广播 / 各面板重建几次 / 多少条广播与本面板无关
opm-ctl --attach auto --cmd '{"op":"ui_stats"}' --json | tail -1 | python3 -m json.tool
# 最近的广播环形日志（话题、来源、撤销标签）
opm-ctl --attach auto --cmd '{"op":"broadcasts","recent":5}' --json | tail -1
# 一键跑完话题分级 + 端到端延迟
python3 scripts/accept-broadcast.py
```

口径（两套计数，量纲不同，别混）：

- `skipped_*`：**逐广播**统计"这条广播的话题与本面板无关"⇒ `broadcasts - skipped_x` = 真正触及该面板的广播数；
- `builds_*`：**逐批**统计实际重建次数，且**逐线**计（"重建了几条线的这一部分"）——
  同一帧到达的多条广播合并成一次重建（实测连发 20 条 → 只重建 2 次），
  所以 `builds_x ≤ broadcasts - skipped_x`，差值就是合并收益。
- 字段：`builds_structure`（判定线整表）/ `builds_props` / `builds_notes` / `builds_tracks` / `builds_meta` / `builds_inspector`。

连"按深色像素找窗口"都会认错窗口（终端底色也接近）。所以验证界面用**应用自截屏**：

opm-app --control auto --shot /tmp/ui.png --shot-frame 40   # 也可以常驻着抓一帧

### 留痕

`--verbose-updates` 把广播链路实时打到 **stderr**（无缓冲，`tail -f` 可用；stdout 重定向到文件是块缓冲，
进程被 SIGTERM 收走时整段留痕会丢 —— 这是踩过的坑）：

```text
[core] update #2 Remote add_event[0:alpha:1] → [Track[0]] → 投递 1/1 订阅者
[update] 演奏区需重绘（轨道改动，无缓存重建）
```

另外：`--attach auto` 会**跳过死进程留下的 socket**（按文件名里的 pid 查 `/proc`）；GUI 正常退出时收走自己的 socket，
被强杀时留下的文件由下次 bind 前清理兜底。

### 实测（2026-09-27，4 条判定线 / 400 音符文档，GUI + `opm-ctl --attach`）

| 命令 | 话题 | Δ整表 | Δ属性 | Δ音符 | Δ轨道 | Δ检查 |
|---|---|---|---|---|---|---|
| `set_meta` | `Meta` | 0 | 0 | 0 | 0 | 0 |
| `add_event`（0 号线 alpha） | `Track[0]` | 0 | 0 | 0 | **1** | 0 |
| `set_track_constant`（3 号线 speed） | `Track[3]` | 0 | 0 | 0 | **1** | 0 |
| `add_note`（2 号线） | `Notes[2],Note[2]` | 0 | 0 | **1** | 0 | **1** |
| 远端 `undo` | `Notes[2],Note[2]` | 0 | 0 | **1** | 0 | **1** |
| `set_line`（1 号线 zOrder） | `LineProps[1]` | 0 | **1** | 0 | 0 | 0 |

**6 条改动，0 次整表重建**；每条改动只重建"它那条线的那一部分"。

延迟拆解（远端 `--attach` → GUI 已应用广播）：

| 段 | 实测 |
|---|---|
| 唤醒 → 应用广播（事件驱动空闲） | p50 **8.3 ms** / last 11.1 ms |
| 唤醒 → 应用广播（`--idle-fps 240` 连续出帧） | p50 **4.56 ms** ≈ 1 帧 @240 Hz |
| 外部客户端观测的端到端 | 12–32 ms（其中 ~7–8 ms 是脚本轮询 `sleep` 的实际粒度，非链路开销） |

⇒ 这一段延迟是**窗口系统出帧调度**（窗口被终端遮挡时更长），与广播链路无关；
`EditCore` 提交到广播投递、再到 GUI 应用，发生在同一帧内（微秒级）。
远端改动之所以能立刻看到，是因为控制线程改完后调用了 `waker()`（`ctx.request_repaint()`）—— 否则空闲心跳下最多要等 1 秒。

证据图：[`artifacts/broadcast-scoped-update.png`](./artifacts/broadcast-scoped-update.png)（最近广播是 `Track[0]`，但谱面/列表/检查器重建计数没动）。
Rust 侧验收：`cargo test --test broadcast`（只命中相关订阅者 / 失败不广播 / 事务与 abort / 撤销也广播）。

## 节奏控制（画面无更新时降为 1 帧，工作时按屏幕帧率）

- **工作态**（播放中 / 正在按住拖拽 / 首帧布局稳定前 / bench 活跃阶段）⇒ 连续 `request_repaint()`，vsync 封顶到屏幕刷新率。
- **空闲态** ⇒ 不连续重绘，只保留 `--idle-fps` 心跳（默认 1）；`--idle-fps 0` 为纯事件驱动。

实测（240 Hz 屏）：

| 状态 | 实测 |
|---|---|
| 工作（播放/基准活跃阶段） | **239.6 fps**（4.174 ms，即屏幕帧率） |
| 空闲，`--idle-fps 1` | **2.50 fps**（eframe 每次唤醒多渲染一帧，故约为设定值的 2 倍） |
| 空闲，`--idle-fps 0` | **1.25 fps**（纯事件驱动，每个空闲窗口仅收尾一帧） |

⚠️ 活动判定**不可**用 `egui_wants_pointer_input()`（鼠标悬停即为真，会把空闲误判为工作，实测把空闲顶到 88~152 fps）；
正确信号是 `egui_is_using_pointer()`（正在按住/拖拽）。

### 事件驱动不止在文档层：表现层也不许每帧白做工

文档层早就是事件驱动的（广播 → 脏位 → 只重建脏的那块）。**表现层**原先还留着几处"每帧重算"，
它们与帧无关，只跟"列表内容 / 当前时刻 / 有没有新广播"有关：

| 原先每帧做的事 | 现在 |
|---|---|
| `filedialog::availability()`：读 `PATH` + 每个候选程序两次 `stat`（约 10 次分配、最多 18 次 stat） | 进程内缓存一次（`OnceLock`），返回 `&'static str`；`detect()` 仍是即问即答的纯探测 |
| 最近打开列表：每条记录一次 `is_file()` + 一次 `format!("[格式] 多久以前")`（最多 20 条） | `recents::list_rows()` 生成**行快照**（标题/副标题/是否存在/悬停文本），只在"列表变了"或"超过 30 秒"时重算（`LIST_ROWS_MAX_AGE`） |
| `env::var("OPM_LAUNCH_AUTO")`（每帧分配一个 String） | 启动时读进 `App::launch_auto`（`OPM_KEY_AUTO` 同理，读进 `App::key_auto`） |
| `publish_stats()`：克隆并**排序最多 512 个延迟样本**、抢 4 次锁、克隆若干字符串 | 最多 10 Hz（`STATS_MIN_INTERVAL`），且收到新广播时立刻补发一次（"等广播被应用"的轮询不用多等一拍） |
| 状态栏/顶栏各一次 `core.lock()` + `path.display().to_string()` + `rsplit` | 文档标识 `[格式] 文件名` **算一次存起来**（`file_badge`，在 `sync_file_fields` / `apply_dirty` 两个事件上刷新），两处重复的显示收成一处 |
| 状态栏对音频路径 `file_name()` + 分配 | `Audio::name()`：载入时算一次 |

**"看起来该缓存"但按实测决定不缓存的**：演奏区实例构建（`render::build_instances`）每帧重建，
但实测 p50 **0.002 ms**（20 万音符的谱面同样，因为只有可见的约 29 个实例会上报）——
为 2 微秒加一层"实例是否需要重建"的门控，换来的是"缓存键漏了一个字段 ⇒ 画面停在旧的一帧"这类难查的 bug，
**不划算**。同理没有给叠加层的网格/刻度缓存：它们每次只是几十次浮点与一次 `format!`。
判断依据是数字，不是"每帧 = 坏"。

## 已实测（2560×1600@240Hz，NVIDIA 5070 / Vulkan，scale 1 与 1.5）

| 场景 | 整帧 p50 | UI 构建 p50 | 实例构建 p50 |
|---|---|---|---|
| 2 万音符（可见 ~29 实例） | 4.171 ms（239.8 fps） | 0.142 ms | 0.002 ms |
| 20 万音符（可见 ~29 实例） | 4.173 ms | 0.143 ms | 0.002 ms |
| 20 万音符 + 全量 20 万实例 | 4.175 ms | 1.127 ms | 0.996 ms |

均已打满 240 Hz 刷新率（4.167 ms）。1.5× 分数缩放下四角/中心标记与 egui 十字完全重合。

## 已知问题（Linux 侧待办）
